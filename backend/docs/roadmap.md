# 백엔드 착수 계획

> **수정 기록 (2026-09-04 ③)** — 계약 v1.4 반영. **`GET /api/session/{id}/live`를 Phase 5에서 떼어 Phase 3 직후로 옮겼다** — 의존이 Phase 3의 `turn_log`·`crisis_event`뿐이고, 앱은 이게 없으면 S02를 끝낼 수 없다(S07 위기 시트·데모 오버레이가 둘 다 여기 걸린다). 종전에는 Phase 5 문서가 "Phase 4보다 먼저 붙여도 된다"고 적어놓고 이 문서의 착수 순서는 5번째에 두어 **두 문서가 같은 것을 다르게 말하고 있었다.**
>
> **수정 기록 (2026-09-04 ②)** — **조직 원리를 "9/10 역산"에서 "의존 순서"로 바꿔 재작성.** PRD §12 개정으로 9/10이 일정 상수에서 **팀 내부 목표**로 내려갔고, **배포는 세 파트 기능 확인 후**로 결정돼(2026-09-04) 종전 "Phase 7의 배포만 9/10 앞으로 당겨진다"가 성립하지 않게 됐다. 착수 블로커 표는 결정된 값으로 교체(스택 4건 확정), 통합 테스트 도달 문제를 신설.
>
> **수정 기록 (2026-09-04 ①)** — 문서 신설.

Phase 문서(`phase-1~7`)가 **무엇을 만드는지**라면, 이 문서는 **어느 것을 먼저 하는지**다. 체크리스트를 여기 복사하지 않는다 — 각 Phase 문서를 가리키기만 한다.

## 일정 (PRD §12, 2026-09-04 개정)

| 날짜 | 항목 | 성격 |
| --- | --- | --- |
| 2026-09-10 | 팀 3인 실사용 시작 | **목표** — 게이트가 아니다 |
| **2026-09-20** | **제출** | **고정** — 외부 마감 |

**배포는 세 파트(앱·백엔드·AI)의 기능 확인이 끝난 뒤에 한다**(팀 결정). 도그푸딩은 웹 링크 공유로 진행되므로 **도그푸딩 시작 시점 = 배포 시점**이다.

> **밀릴 때의 대가는 알고 밀어야 한다.** 개발은 압축할 수 있어도 로그는 압축되지 않는다. 도그푸딩 기간이 짧아지면 관찰 생성 조건(태그 3회 이상 AND 개인 평균 갭 1.5배 이상, FR-051)에 미달하고, **조건 미달이면 억지 관찰을 만들지 않는 것이 이 제품의 설계이므로**(FR-052) S03 발견 화면이 정직하게 빈 채로 심사받게 된다. 이건 코드로 되돌릴 수 없는 유일한 항목이다.

## 착수 순서 (의존 관계 — 날짜 없음)

```
0. 스택 확정 ✅ + Hume 플랜 결제 ⏳     ← 0번이 안 끝나면 1번을 시작할 수 없다
1. Phase 1  골격 · docker-compose · 스키마 11테이블 · 인증 · 헬스체크
2. Phase 2  세션 + GET /internal/sessions   ← 앱·AI가 동시에 풀린다
3. Phase 3  /internal/turns 수신 · 암호화 저장  ← 여기서 로그가 쌓이기 시작한다
   ├ GET /api/session/{id}/live               ← 앱이 S02를 끝내려면 필요 (S07 · 데모 오버레이)
   └ AI와 통합 테스트 (터널) — request/ai/integration-test-path.md
4. Phase 4  패턴 배치
5. Phase 5  조회 API (관찰 · 트렌드 · 기록)
6. Phase 6  삭제 · 탈퇴                  ← 제출 전 필수 (FR-003)
7. Phase 7  데모 모드 · 오류 로깅
─────── 세 파트 기능 확인 완료 ───────
8. 배포 (Render) + cron 킵얼라이브 → 도그푸딩 시작
```

**Phase 2·3이 가장 앞에 오는 이유**는 이 둘이 다른 두 역할을 동시에 막고 있기 때문이다 — 앱은 `POST /api/session/start` 없이 EVI에 붙지 못하고, AI는 `GET /internal/sessions/{id}` 없이 CLM 인증을 통과하지 못한다.

일정이 밀릴 때 버리는 순서는 `../../docs/00-context/spec.md` §11(스코프 컷 순서)이 단일 기준이다. **이 문서가 그 순서를 바꾸지 않는다** — 여기서 정하는 건 "먼저 할 것"뿐이고 "버릴 것"은 spec이 정한다.

## Phase별 성격

| Phase | 다른 역할을 막는가 | 데이터 축적에 필요한가 | 제출에 필수인가 |
| --- | --- | --- | --- |
| 1 골격·인증 | 앱 로그인 | ○ (세션의 전제) | ○ |
| **2 세션** | **앱 EVI 연결 · AI CLM 인증** | **○** | ○ |
| **3 턴 수신 + `/live`** | **앱 S02 완성**(S07 위기 시트·데모 오버레이) | **○ — 이게 없으면 로그가 0건** | ○ |
| 4 패턴 배치 | — | ✕ (과거 턴을 다시 읽어 소급 집계) | ○ |
| 5 조회 API | 앱 화면 4개 | ✕ | ○ |
| 6 삭제·탈퇴 | — | ✕ | **○ (FR-003)** |
| 7 데모·로깅 | 앱 데모 배지 | ✕ | 데모 모드만 |

**Phase 4~7이 뒤로 가도 되는 이유**는 배치가 과거 턴을 다시 읽기 때문이다. 9/15에 패턴 배치를 만들어도 그 전에 쌓인 로그가 전부 집계된다. 반대로 **Phase 3이 늦으면 그 기간의 로그는 영영 없다.**

## 통합 테스트 — 로컬끼리는 도달하지 못한다

배포를 뒤로 미루면서 생긴 문제다. **AI서버는 AI 담당 PC, 백엔드는 내 PC**에 있어서, AI서버가 부르는 `POST /internal/turns`·`GET /internal/sessions/{id}`가 도달할 경로가 없다(각자에게 `localhost`는 자기 PC다).

- 반대 방향(백엔드 → AI서버)은 **AI서버가 Hume 때문에 이미 ngrok으로 열려 있어** 문제없다
- 백엔드도 **통합 테스트 동안만 터널을 연다.** 배포가 아니라 임시 경로다
- 시점·순서는 협의 중 — `../../docs/request/ai/integration-test-path.md` (⏳)
- 붙이는 순서는 **`GET /internal/sessions/{id}`부터**. CLM 인증 경로라 이게 안 되면 나머지가 전부 401로 막혀 검증이 성립하지 않는다

## 다른 역할이 백엔드를 기다리는 것

| 상대 | 기다리는 것 | 전달 시점 |
| --- | --- | --- |
| 앱 | `humeConfigId` (session/start 응답) | Phase 2 |
| 앱 | 백엔드 주소 (`API_BASE_URL`) | 통합 시 터널 URL → 배포 후 정식 도메인 |
| AI | `X-Internal-Secret` 값 | 통합 시작할 때. 저장소에 넣지 않는다 |
| AI | `GET /internal/sessions/{id}` 실동작 | Phase 2 — **CLM 인증이라 AI 개발을 막는다** |
| AI → 백엔드 | Hume Config 생성 후 `config_id` | AI가 생성·소유. 받으면 환경변수에 넣는다 |
| AI → 백엔드 | `turnIndex` 채번 확인 (`request/ai/turn-index-numbering.md` ⏳) | **F2-07(이어하기)을 붙이기 전.** 리셋하면 이어하기 이후 턴이 조용히 유실된다 |
| 앱 | `GET /api/session/{id}/live` | **Phase 3** — S02가 이걸로 완성된다 |
| 앱 | `tagGaps`·`userAvgGap` (F9-03, P1) | Phase 5 — 계약 v1.4로 확정됨 |
