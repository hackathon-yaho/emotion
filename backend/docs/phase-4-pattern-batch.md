# Phase 4 — 패턴 배치

> 목표: **쌓인 턴에서 관찰이 생기는 상태**를 만든다. 조회 화면은 아직 없어도 된다.
>
> 의존: Phase 3이 적재한 `turn_log`·`turn_tag` 데이터 · Phase 1의 스케줄러 뼈대와 `observation`·`observation_evidence` 테이블 · Phase 2가 기록하는 `ended_at`
>
> 근거: `spec.md` F7-01~05 · `api-contract.md` §3-3 · PRD FR-050~054

> **상태 (2026-09-05): 코드 완료 · 테스트 59건 통과.**
> **AI서버가 없어 문장화가 항상 실패하므로 지금은 관찰이 하나도 생기지 않는다** — 그게 설계대로다(템플릿 폴백 없음). 판정 로직은 테스트로 못 박았고, `/internal/sessions`의 `recentObservations`는 실서버에서 실제 값이 나가는 것을 확인했다.

> **이 Phase는 늦어도 된다.** 배치가 과거 턴을 다시 읽으므로, 나중에 만들어도 그 전에 쌓인 로그가 전부 집계된다 — `roadmap.md`. 대신 **판정 로직은 절대 타협하지 않는다**(4-3).

## 4-1. 배치 트리거 (F7-01)

- [x] Phase 1의 스케줄러에 태운다 — **F2-06 정리·헬스체크와 같은 스케줄러**
- [x] 매 주기 스캔

```sql
select id from voice_session
 where ended_at is not null
   and pattern_processed_at is null
```

- [x] 처리 성공 시에만 `pattern_processed_at = now()` 기록
- [x] **배치 실패가 대화·조회 기능에 영향을 주지 않는다** (F7-01 수용 기준) — 예외를 삼키고 다음 세션으로 넘어간다

> **왜 인메모리 큐(`@Async`)가 아닌가** — Render는 15분 무트래픽에 슬립하고 재배포도 잦다. 인메모리 큐는 그때 증발하고, **그 세션은 관찰이 영영 안 생기는데 아무도 모른다.** 컬럼 방식은 다음 주기에 자동으로 주워간다. F2-06이 "끊긴 세션"을 막으려고 만든 장치인데 같은 사고가 배치에서 반복되면 의미가 없다.

> 실패 시 `pattern_processed_at`이 NULL로 남아 **자동 재시도**된다. 별도 재시도 카운터를 두지 않는다 — 같은 세션이 계속 실패하면 `ops_error_log`에 반복해서 남으므로 그것으로 알아챈다.

## 4-2. 태그별 집계 (F7-02)

- [x] 사용자 **전체 기간**의 태그별 집계 (이번 세션만이 아니다)
- [x] 태그별 `occurrences`(등장 턴 수), `tagAvgGap`(그 태그 턴들의 평균 갭)
- [x] `userAvgGap` — 그 사용자 전체 턴의 평균 갭
- [x] `ratio = tagAvgGap / userAvgGap`
- [x] **갭이 `NULL`인 턴은 전부 제외** — 분모·분자 양쪽에서

> `user_baseline.avg_gap`(Phase 3)과 여기서 계산하는 `userAvgGap`은 **같은 값이어야 한다.** 한쪽만 갱신되면 관찰의 `evidence` 숫자와 트렌드 화면이 어긋난다. **`user_baseline`을 읽어 쓰고 여기서 다시 계산하지 않는다.**
>
> **`GET /api/trend`의 `userAvgGap`(계약 §2-8, v1.4)도 같은 값이다.** 세 곳(baseline·관찰 evidence·트렌드 응답)이 전부 `user_baseline.avg_gap`을 읽는다. 조회 시점에 다시 계산하는 코드를 만들면 §1.4 "evidence 불일치 0건"이 그 순간 깨진다.

## 4-3. 규칙 판정 (F7-03) — **코드가 판정한다**

- [x] `occurrences >= 3` **AND** `tagAvgGap >= userAvgGap × 1.5`
- [x] **미달이면 아무 관찰도 만들지 않는다.** 억지로 통찰을 생성하지 않는다

> **여기에 LLM 호출을 섞지 않는다** — 백엔드 절대 원칙 1번, FR-051·052. LLM에 로그를 통째로 주면 그럴듯한 패턴을 **반드시** 만들어낸다. 판정을 규칙으로 고정해야 모든 관찰이 숫자로 역추적된다.
>
> **매일 통찰을 뱉는 앱은 신뢰를 잃는다 — 침묵할 수 있어야 말할 때 믿긴다.** 데이터가 부족한 사용자에게 관찰이 안 생기는 것은 버그가 아니라 사양이다(TC-16).

## 4-4. 관찰 문장 생성 (F7-04) — `POST /internal/observations`

- [x] 판정을 **통과한 것만** AI서버에 보낸다 — 요청·응답은 계약 §3-3
- [x] 보내는 것은 **숫자와 태그뿐이다.** 원본 대화·발화·turn ID를 넣지 않는다
- [x] 응답의 `sentence`를 `observation.sentence`에 저장
- [x] **실패하면 관찰을 만들지 않는다.** 템플릿 문장으로 대체하지 않는다

> **원본 대화를 보내지 않는다**(계약 §3-3). LLM은 표현만 담당하고 패턴의 존재·강도를 판정하지 않는다(FR-054).
> **템플릿 폴백을 두지 않는 이유** — 표현이 어색한 것보다 **근거 없는 문장이 나가는 쪽이 위험**하다. 실패하면 다음 주기에 다시 시도된다(4-1).

## 4-5. evidence 부착 (F7-05)

- [x] `observation`에 집계 결과를 그대로 저장 — `tag`·`occurrences`·`tag_avg_gap`·`user_avg_gap`·`ratio`. **계약 §2-6의 `evidence` 객체가 이 5개다**(`tag` 포함)
- [x] 근거 turn을 `observation_evidence`에 연결
- [x] **API 응답의 `evidence` 객체에는 turn ID를 넣지 않는다**(계약 §2-6). 근거 대화는 F7-07 상세 조회의 `turns` 배열로만 내려간다

> **관찰 문장 ↔ evidence 숫자 불일치는 0건이어야 한다**(§1.4 핵심 지표). AI가 돌려준 문장의 숫자를 다시 파싱해 검증하지 않는다 — 애초에 **우리가 보낸 숫자를 그대로 저장**하므로 불일치가 생길 경로가 없다. 문장이 숫자를 왜곡했다면 그건 프롬프트 문제이고 AI 쪽에서 잡는다.

## 완료 기준

- ✅ 세션 종료 후 다음 스케줄러 주기에 배치가 돈다 — 종료되지 않은 세션은 대상이 아닌 것까지 확인
- ✅ 조건을 넘긴 태그에만 관찰이 생기고, `observation_evidence`에 근거 turn이 연결된다
- ✅ **TC-16** — 태그가 2회만 등장한 사용자에게 **관찰이 생성되지 않는다** (비율이 아무리 커도)
- ✅ **TC-17** — 관찰의 `evidence` 숫자와 실제 근거 대화 건수가 일치한다 — 집계와 근거 조회가 **같은 조건**을 쓴다
- ✅ 배치가 실패해도 `POST /api/session/start`·조회 API가 정상 동작한다 — 스케줄러가 예외를 삼킨다
- ✅ 서버를 재시작해도 미처리 세션이 다음 주기에 처리된다 — `pattern_processed_at`이 NULL로 남는다
- ✅ `api-spec.md`에서 `/internal/observations`를 `구현 완료`로 갱신했다
- ✅ **관찰이 실제로 한 건 생겼다** (2026-09-05) — 갭 1.50짜리 `회의` 턴 3건 + 갭 0.10짜리 `산책` 턴 3건을 넣고 세션을 종료하니, 배치가 **`회의`만** 관찰로 만들고 `산책`은 침묵했다. `evidence`는 `occurrences 3 · tagAvgGap 1.50 · userAvgGap 0.80 · ratio 1.88`, 근거 대화 3건이 연결됐고 `GET /api/observations`에 그대로 나온다
  - **문장화는 대역 서버로 받았다.** 진짜 AI서버는 LLM 키(`GOOGLE_API_KEY`)가 없어 422로 떨어지는데, 그러면 **실패 경로만 확인되고 성공 경로는 한 번도 안 돈다.** 단위 테스트는 클라이언트 자체를 목으로 바꿔서 **HTTP 계층이 실행된 적이 없었다** — 헤더·직렬화·타임아웃이 전부 미검증이었다
  - **AI서버로 나간 본문을 눈으로 확인했다** — `{tag, occurrences, tagAvgGap, userAvgGap, ratio}` 다섯 개뿐이고 원본 대화·turn ID가 없다(계약 §3-3)
- ⏳ **진짜 문장으로 한 건** — `GOOGLE_API_KEY`가 들어오면 끝난다. 남은 것은 AI 쪽 몫이다 (LLM 벤더가 2026-09-05에 Gemini로 바뀌었다)
- ✅ `/internal/sessions`의 `recentObservations` — 실서버에서 실제 값이 나가는 것 확인 (Phase 2 코드에 연결)

> **같은 태그로 이미 살아 있는 관찰이 있으면 새로 만들지 않는다** (2026-09-05 결정, spec에 규정이 없던 부분). 집계가 전체 기간이라 한 번 조건을 넘긴 태그는 **세션마다 계속 넘긴다** — 그대로 두면 발견 화면이 같은 문장으로 도배되고 AI 호출도 매번 나간다. **관찰은 시점의 발견으로 두고**, 숫자가 자라도 갱신하지 않는다(evidence는 그때 센 턴들을 가리킨다). **더 강한 패턴으로 갱신할지는 도그푸딩 뒤에 정한다.**

> **AI 호출이 트랜잭션 안에서 일어난다** (알려진 한계). 태그마다 최대 10초를 잡고 그동안 커넥션 하나를 쥔다. 인스턴스 1개·사용자 3인 규모에서는 문제가 되지 않지만, **사용자가 늘면 배치를 트랜잭션 밖으로 빼야 한다.**
