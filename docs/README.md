## 핵심 설계 원칙 (전원 필독)

> **절대 감정을 단정하지 않는다.** 이 제품의 주장은 "같은 말을 다르게 하면 갭이 갈린다"뿐이다(PRD §1.4). 갭 = |텍스트 valence − 음성 valence|이고, 임계 초과 시 AI가 **되묻는다** — 단정하지 않는다(FR-022·030). 갭 수치는 기록·트렌드 화면에서만 보이고 대화 화면에는 나오지 않는다(FR-031).

> **판정은 코드, 표현은 LLM.** 음성 valence 환산(FR-020), 갭 계산(FR-022), 관찰 생성 조건(FR-051)은 전부 결정적 규칙이다. LLM은 대화 응답·태그·관찰 **문장**만 만든다(FR-054). 태그는 발화 원문에 등장한 표현만 허용하고 코드가 대조한다(FR-043). 관찰에는 evidence가 반드시 붙고, 문장 ↔ 숫자 불일치는 **0건**이어야 한다(§1.4).

> **오탐 정책은 기능군마다 반대다.** 갭·패턴은 **정밀도 우선**(애매하면 침묵), 위기 감지는 **재현율 우선**(애매하면 감지). 위기 감지는 규칙 OR LLM이며, LLM이 죽어도 키워드 규칙은 단독으로 동작한다(FR-032). 감지 시 109를 안내하되 **대화를 끊지 않는다**(FR-033). F4는 어떤 스코프 컷에서도 자르지 않는다(spec §11).

> **음성 원본은 우리 서버에 오지 않는다.** 앱↔Hume 구간에만 존재하며, AI서버는 텍스트와 점수만 받는다(FR-041·§5.1). 발화 텍스트는 암호화 저장, 카카오 식별자는 감정 데이터와 분리, 탈퇴는 유예 없이 전량 삭제.

이 원칙이 무너지면 심사 방어 논리 전체가 흔들립니다. 앱은 대화 화면에 갭 수치를 그리지 않고, 백엔드는 관찰 판정에 임의 로직을 섞지 않으며, AI는 프롬프트로 판정을 대신하지 않습니다.

| `response/backend/*` | 백엔드가 보낸 요청에 대한 회신 | BE |
| `response/ai/*` | AI 담당자가 보낸 요청에 대한 회신 | AI |
| `../ai-server/` (프롬프트 파일) | **프롬프트 전문의 단일 출처.** 문서에는 조항 요지만 둔다 (PRD §9.3) | AI |

`01-product/`는 디자인 시스템 문서와 함께 만들었습니다(2026-09-03). 해빙에 있던 `03-infra-ops/`, `04-testing/` 폴더는 지금은 비어 있어 만들지 않았습니다. 해당 성격의 문서(페르소나 분리, 배포·프라이버시, 테스트·데모)가 PRD·spec에서 갈라져 나올 때 같은 번호로 만듭니다.

## 문서 갱신 규칙

- `request/app/*`, `request/backend/*`, `request/ai/*`는 **다른 역할에게 보내는 요청 문서**만 담습니다(요청 하나당 파일 하나). 갭 계산 규칙, API 스키마 같은 실제 스펙 본문을 복사해 넣지 마세요 — 스펙이 바뀌면 두 곳을 다 고쳐야 하고, 결국 어긋납니다. 스펙이 바뀌면 `00-context/`, `02-architecture/` 원본만 고치고 request는 그대로 둡니다.
- **요청 문서 맨 위에 회신 상태 배너를 답니다** (⏳ 회신 대기 / ✅ 회신 완료 / ⚠️ 일부 회신). 요청만 쌓이면 어느 게 아직 살아 있는 요청인지 알 수 없습니다. 회신이 와도 **요청 본문은 고치지 않고** 배너만 바꿉니다 — 당시 무엇을 물었는지가 기록이기 때문입니다. 형식은 `request/app/README.md` "회신 상태 표시 규칙" 참조. (해빙은 이 규칙을 나중에 추가했는데 그 전에 "요청이 반영됐는지 확인할 방법이 없다"는 문제를 겪었습니다. 처음부터 둡니다.)
- **요청을 처리했으면 `response/{요청한 사람}/`에 회신 문서를 남깁니다** (회신 하나당 파일 하나, 파일명은 원본 요청과 동일하게). **폴더 이름이 이 문서를 읽을 사람**입니다 — 백엔드가 AI에게 보낸 요청은 `request/ai/`에, 그 회신은 `response/backend/`에 둡니다. **반영하지 않기로 한 경우에도 이유를 적어 회신합니다.** 자세한 규칙은 `response/README.md` 참조.
- PRD·기능명세서 자체를 수정해야 하는 결정(요구사항 변경, 스코프 조정)이 생기면 `00-context/prd.md`(필요 시 `spec.md`도)를 고치고, 그 사실을 팀 채널에 공유하세요. **필드를 추가·삭제·개명하려면 `02-architecture/api-contract.md`를 먼저 고치고 버전을 올린 뒤** 코드를 바꿉니다(계약서 §6 변경 절차).
- **스펙·계약 문서를 고쳤으면, 같은 작업 안에서 각자의 실행 계획 문서도 확인하세요.** 파생 문서는 자동으로 따라오지 않습니다. 해빙에서는 이 규칙이 없어 백엔드 문서 6개가 하루치만큼 낡은 적이 있습니다.
- 이 파일 맨 위 **수정 기록 배너**에 문서 변경 사항을 날짜와 함께 남깁니다. 지난주에 읽은 사람이 무엇이 바뀌었는지 배너만 보고 알 수 있어야 합니다.
