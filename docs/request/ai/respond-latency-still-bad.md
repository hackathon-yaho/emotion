# 응답 사다리를 넣은 뒤에도 응답이 12~47초입니다 — 사용자가 나간 뒤에 답이 도착합니다

> **상태: ✅ 회신 완료 (2026-09-08)** — [`../../response/backend/respond-latency-still-bad.md`](../../response/backend/respond-latency-still-bad.md)
> **원인은 응답 모델입니다 — `gemini-3.8-flash`의 TTFT가 188초입니다**(같은 키·같은 시각 실측). 같은 요청 안에서 분석은 1.0~1.2초에 끝납니다 — **둘은 모델이 다르고, 느린 것은 응답 하나뿐입니다.** 응답·관찰을 `gemini-3.5-flash-lite`(1.4초)로 옮기고, **첫 글자에 5초 시한**을 걸어 넘으면 다음 칸으로 갈아타게 했습니다. 배포했습니다(revision 00010).

> **부탁은 하나입니다** — Cloud Run 로그에서 이 지연의 정체를 확인해 주십시오. **gcloud가 제 PC에 없어 제가 못 읽습니다.**

## 증상 — 첫 음성만 나오고 그 뒤로 안 나옵니다

첫 인사는 Hume Config가 내는 것이라 CLM 없이 나옵니다. **그러니 이 증상은 「첫 CLM 호출부터 전부 실패」로 읽어야 합니다.**

**다만 실패가 아닙니다.** 응답은 만들어집니다 — **너무 늦게** 만들어집니다.

**세션이 끝난 뒤에 응답 두 건이 도착했습니다.** Hume은 CLM 응답을 무한정 기다리지 않으니, 이 답들은 음성으로 나갈 자리가 이미 없었습니다.

## 백엔드는 목이 아닙니다 — 같은 표로 보입니다

`ingest_lag`(= `created_at − occurred_at`, AI서버가 `POST /internal/turns`로 우리에게 턴을 넣은 지연)이 **17건 전부 0.6~0.9초**입니다. 편차도 없습니다.

**응답이 47초 걸린 그 턴의 ingest_lag도 0.6초입니다.** 우리 왕복이 느려서 생긴 지연이면 이 값이 같이 커져야 하는데 그렇지 않습니다. 세션 조회(§3-4)는 세션당 1회 캐시라 2번째 턴부터는 호출조차 없습니다.

**앱도 아닙니다.** 재생 큐 문제라면 응답이 제때 만들어지고 소리만 안 났을 텐데, 생성 시각 자체가 늦습니다.

## 부탁드리는 것

**① Cloud Run 로그에서 이 시각들의 응답 경로를 봐 주십시오.** 특히 13:15~13:19 구간입니다. `respond-fallback-cause.md`에서 만드신 태그면 바로 갈릴 것 같습니다 — `llm_rate_limited` · `respond_failed:RateLimitError:429` · 사다리를 몇 칸 탔는지.

**② 사다리가 지연으로 바뀐 것은 아닌지 봐 주십시오.** 429에 정형 문장 대신 다른 조합으로 갈아타게 하셨는데, **한 칸씩 갈아탈 때마다 초가 붙습니다.** 실패가 사라진 대신 지연이 된 것이라면, 사용자에게는 **정형 문장이라도 3초에 오는 편이 나을 수 있습니다** — 47초 침묵보다는요. 판단은 그쪽 몫입니다.

**③ 배포본이 쓰는 키가 몇 개인지 확인 부탁드립니다.** 팀장 확인으로는 **팀원이 각자 개인 키를 쓰고 있습니다.** 다만 그건 로컬 `.env` 이야기고, **배포된 Cloud Run은 Secret Manager의 값을 씁니다.** `GOOGLE_API_KEY_2`·`GOOGLE_API_KEY_3`이 Secret Manager에 실제로 들어가 있는지, 사다리가 여벌 키를 타고 있는지가 로그에 나올 것 같습니다. **두 이야기가 동시에 참일 수 있어서 적습니다** — 각자 키를 써도 배포본은 한 개로 돌 수 있습니다.

## 제가 확인해 드릴 수 있는 것

`turn_log`는 제 것이라 언제든 다시 뽑아 드립니다. **턴별 지연·ingest_lag·세션 경계**를 원하시는 구간으로 잘라 드릴 수 있습니다. 발화 내용은 암호화돼 있고 이 요청에도 넣지 않았습니다(FR-092).

**분수 걱정은 하지 않으셔도 됩니다** — 위 데이터는 이미 한 대화들에서 나온 것이고, 새로 대화를 걸어야 나오는 정보가 아닙니다.
