## 무엇을 봤나

`GET /api/observations/{id}/evidence` 응답의 `turns[].transcript`에 **영문 감정 표현이 중괄호로 꼬리처럼 붙어** 나옵니다.

```
"아 내가 이거 합격하면은 좀. {slightly doubtful, slightly calm, very slightly interested}"
```

앞의 한글까지가 사용자가 실제로 말한 문장이고, `{...}`는 사용자가 말한 적 없는 문자열입니다.

## 원인 추정 — Hume이 프로소디를 두 번 보냅니다

Hume은 같은 프로소디를 **① 구조화된 `models.prosody.scores`** 로 한 번, **② CLM 프롬프트용으로 발화 본문 끝에 덧붙인 영문 형용사**로 또 한 번 보냅니다. ②는 프로소디를 못 받는 LLM을 위한 Hume 쪽 편의 기능인데, 우리는 ①을 쓰므로 ②는 순수한 오염입니다.

`ai-server/app/clm/request.py:38`의 `Message.content`가 그 문자열을 **가공 없이** 들고, `transcript()`(`:64`)와 `text_history()`(`:76`)가 그대로 내보내는 것으로 보입니다.

> 앱이 EVI 소켓에서 직접 받는 전사에는 안 붙는 것 같습니다 — 대화 화면에서는 보이지 않았고 **CLM을 거쳐 저장된 기록에서만** 나왔습니다. 그래서 유실 지점이 CLM 파싱이라고 봤습니다.

## 표시만의 문제가 아닙니다 — 텍스트 경로 전체가 이 문자열을 봅니다

`main.py:176`의 `transcript`가 아래로 전부 흘러갑니다.

| 쓰이는 곳 | 코드 | 걸리는 규칙 |
| --- | --- | --- |
| 텍스트 valence 분석 LLM 입력 | `main.py:206` → `llm/analyze.py` | **FR-025.** 프로소디가 텍스트 채널에 다시 합류합니다 — 갭의 전제(두 채널 독립)가 깨집니다 |
| 응답 LLM 입력(이력) | `text_history()` | **FR-025.** 응답 LLM에는 플래그만 가야 하는데 수치 대신 형용사가 갑니다 |
| 태그 원문 대조 | `main.py:228` → `rules/tags.py:31` | **FR-043.** `calm`·`interested` 같은 표현이 "발화 원문에 등장"한 것으로 통과할 수 있습니다 |
| 위기 키워드 규칙 | `main.py:196` | 오탐·누락 가능성(확인 필요) |
| 백엔드 저장 → 기록·근거 화면 | `main.py:245` → 계약 §3-2 | 사용자가 말하지 않은 문장이 자기 기록으로 보입니다 |

**갭이 흔들릴 수 있다는 게 가장 무겁습니다.** 텍스트 valence LLM이 영문 감정어를 읽으면 음성 valence와 상관이 생기고, 그만큼 갭이 실제보다 작아집니다. 지금까지 측정한 갭 값은 이 영향을 받았을 수 있습니다.

## 부탁드립니다

1. **파싱 시점에 한 번만 떼어주세요.** `Message.content`가 지나는 자리가 한 곳이라, 거기서 잘라내면 위 표의 다섯 경로가 같이 해결됩니다. 아래로 내려간 뒤에 각자 처리하면 빠지는 경로가 생깁니다.
   ```python
   _PROSODY_SUFFIX = re.compile(r"\s*\{[A-Za-z ,'\-]*\}\s*$")
   ```
   영문 문자만 매칭하면 한글 발화 속 중괄호(`{진짜 괜찮았어요}`)는 안 건드립니다. 제안일 뿐이고 판단은 맡깁니다.
2. **Hume Config에서 이 주입을 끌 수 있는지** 확인해 주세요. 끌 수 있다면 그쪽이 근본이고, 파서 방어는 그대로 두면 됩니다(다음에 켜져도 안 샙니다).
3. **로그로 실제 모양을 확인해 주세요.** `{}` 안 구분자·순서·개수, 그리고 **assistant 메시지에도 붙는지**. 위 정규식은 쉼표 구분·본문 맨 끝을 가정합니다.
4. **회신에 「언제부터 붙었는지」를 적어 주세요.** 저장된 턴 중 어디까지가 오염됐는지 판단해야 합니다.

## 백엔드가 하는 것 / 안 하는 것

- **안 합니다 — 적재 시점 방어적 제거.** 계약 §3-2의 `transcript`는 "발화 원문"이고, 백엔드가 받은 값을 고치기 시작하면 원문의 정의가 두 군데로 갈라집니다. 파서에서 고치는 쪽이 맞다고 봅니다. **AI 쪽 수정이 늦어져 임시 방어가 필요하면 말씀해 주세요** — 넣고, 파서가 고쳐지면 뺍니다.
- **못 합니다 — 이미 저장된 턴 정리.** `transcript_enc`는 애플리케이션에서 암호화해 넣어 SQL로 일괄 수정이 안 됩니다. 필요하면 복호화–재암호화 일회성 작업을 따로 돌려야 하는데, **시연 데이터를 새로 만드는 게 더 쌉니다.** 회신 4번을 보고 정하겠습니다.
