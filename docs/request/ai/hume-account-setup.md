## 결정 — 계정은 AI가 만들고 소유합니다

알려주신 문제(`config_id`가 워크스페이스에 묶여서 Config 계정과 결제 계정이 갈리면 쿼터가 적용되지 않는 것)에 대한 팀 결정입니다.

**AI 쪽에서 계정을 만들어 소유해 주세요.**

- **테스트를 전부 AI 쪽에서 진행합니다.** 계정을 다른 사람이 들고 있으면 Config 설정·수정마다 왕복이 생깁니다
- **대시보드를 봐야 하는 쪽도 AI입니다** — 사용량·세션 로그·에러를 실시간으로 봐야 하는 건 EVI를 직접 붙이는 쪽입니다
- 백엔드는 그 계정에서 발급된 **API 키와 `config_id`만** 받아 환경변수에 넣습니다

**결제도 그 계정 위에서 합니다.** 그게 이 문제의 요건 전부입니다 — 카드 주체와 정산은 팀 내부에서 처리하고, 기술적으로 지켜야 하는 건 **"결제가 Config를 만든 계정에서 이뤄질 것"** 하나입니다.

## 예산 — 크리에이터 플랜까지 승인합니다

**상한을 Creator 플랜까지로 둡니다.** 그 아래에서 충분하면 낮은 플랜으로 가세요 — 상한이지 지정이 아닙니다.

판단에 필요한 사실을 정리하면 —

| 항목 | 값 | 출처 |
| --- | --- | --- |
| 필요 분량 | **약 490분** (개발 테스트 300 + 도그푸딩 90 + 리허설·본선 100) | PRD §11 |
| 필요 동시 접속 | **3** (3인 도그푸딩) | PRD §11 |
| Starter 동시 접속 | **5** | 알려주신 값 (2026-09-04) |

**동시 접속만 보면 Starter로 충분합니다**(5 ≥ 3). 그래서 상위 플랜의 값어치는 **포함 분수와 초과 단가**에 있습니다 — 490분을 어느 쪽이 싸게 넘기는지가 기준입니다.

## 요청 — 콘솔에서 확인하고 알려주세요

PRD §2.5가 **3자 문서의 요금 정보를 확정값으로 쓰지 않는다**고 못박아서, 결제 전에 콘솔에서 실측이 필요합니다. 계정을 만드시면서 같이 봐 주세요.

1. **플랜별 포함 분수와 초과 단가** — Starter / Creator 각각. 490분 기준으로 총액을 비교할 수 있게
2. **플랜별 동시 접속 수** — Starter 5는 알려주셨고, Creator 값
3. **신규 계정 $20 크레딧이 EVI 사용료에 적용되는지** — 적용되면 490분이 사실상 덮여 PRD §11의 약 $37 추산이 크게 달라집니다
4. **결제 수단을 등록할 위치** — 그 계정의 Billing에 등록하면 되는지, 팀/워크스페이스 단위 결제가 별도로 있는지

**총액이 예상을 넘으면 결제 전에 알려주세요.** 승인 상한은 Creator 플랜이지만, 초과 사용료까지 포함한 총액은 함께 보고 정하겠습니다.

## 결정하고 나면 백엔드에 넘겨주실 것

| 항목 | 쓰이는 곳 |
| --- | --- |
| **Hume API 키** | 백엔드 환경변수 `HUME_API_KEY`. **단기 액세스 토큰 발급에만** 씁니다 — 앱에는 절대 내려보내지 않습니다(FR-013·TC-03) |

## 참고 — 이게 9/6을 막습니다

통합 순서 1번이 `GET /internal/sessions/{id}`라 그 자체는 Hume 없이도 검증됩니다. 다만 **EVI를 실제로 붙이는 순간부터는 유료 플랜이 필요**하고, Free는 하드 컷 7분짜리 세션 **하나가 월 할당량(5분)보다 깁니다.** 계정·결제가 늦어지면 9/6에 붙일 수 있는 것이 내부 API 4종까지로 줄어듭니다.

# 추가 (2026-09-04) — 넘겨주실 키가 **두 개**입니다

위 "결정하고 나면 백엔드에 넘겨주실 것" 표에 `HUME_API_KEY` 하나만 적었는데, **하나가 빠졌습니다.**

| 항목 | 백엔드 환경변수 | 쓰임 |
| --- | --- | --- |
| API 키 | `HUME_API_KEY` | 아래와 짝 |
| **Secret 키** | **`HUME_SECRET_KEY`** | **단기 액세스 토큰 발급에 둘 다 필요합니다** |
| Config ID | `HUME_CONFIG_ID` | `session/start` 응답으로 앱에 전달 |

**계약 §2-4의 `humeAccessToken`이 이 두 키로 만들어집니다.** 앱에는 그 단기 토큰만 내려가고 두 키는 서버 밖으로 나가지 않습니다(FR-013·NFR-04, TC-03).

콘솔에서 키를 확인하실 때 **Secret 키도 같이** 주시면 됩니다. **셋 다 저장소에 넣지 않습니다** — `X-Internal-Secret`과 같은 경로로 부탁드립니다.

## 덧붙임 (2026-09-04 밤) — `GET /internal/sessions/{id}`가 돌아갑니다 + 공유 시크릿을 어떻게 드릴까요

### 1. 통합 순서 1번이 백엔드 쪽에서 준비됐습니다

회신에서 합의한 순서(`GET /internal/sessions` → `/internal/turns` → …)의 **첫 칸이 열렸습니다.** 계약 §3-4 그대로 나갑니다.

- `X-Internal-Secret` 없거나 틀리면 **401 `INTERNAL_AUTH_FAILED`** (JWT로는 통과하지 못합니다)
- 없는 `sessionId` → **404**
- **`status: "ended"`도 200**입니다 — 401로 바꾸는 판단은 그쪽 몫이라는 계약 그대로입니다
- **`lastTurnIndex`는 적재된 최대 인덱스**입니다(건수가 아닙니다). 지금은 턴이 없어 항상 `0`이고, 그쪽 카운터 시드가 그대로 성립합니다
- **`recentObservations`는 빈 배열**입니다 — 관찰은 Phase 4에서 생깁니다. 값이 없는 게 아니라 아직 없습니다

`ai-server/eval/fixtures/internal/`의 고정 JSON과 맞춰보시면 터널 전에 형태를 확인하실 수 있습니다.

### 2. `INTERNAL_SHARED_SECRET` 값을 아직 아무도 만들지 않았습니다

양쪽 `.env.example`에 **변수만 있고 값이 없습니다**(`ai-server/.env.example:13`, `ai-pipeline.md` §환경변수). 같은 값이어야 하므로 누군가는 만들어서 건네야 하는데, **엔드포인트를 가진 쪽이 만드는 게 맞다고 보고 백엔드가 만들겠습니다.**

**어느 경로로 드리면 될지 알려주세요.** 저장소에는 넣지 않습니다(계약 §3-1). 카카오 JS 키를 앱에 전달하는 건과 같은 질문이라 경로를 하나로 정하면 편할 것 같습니다.

### 3. Hume 키 3개가 지금 무엇을 막고 있는지 (진행 상황 공유)

`POST /api/session/start`는 **다 만들어졌고 지금은 503 `HUME_TOKEN_ISSUE_FAILED`로 떨어집니다** — `.env`에 자리표시가 들어 있어서입니다. 키가 오면 그 자리에서 끝납니다.

- 발급 방식은 `POST https://api.hume.ai/oauth2-cc/token`에 **API 키·Secret 키를 Basic 인증**으로 보내는 `client_credentials`입니다(만료 30분, 하드컷 7분이라 넉넉합니다)
- **`HUME_CONFIG_ID`는 없으면 서버가 아예 기동하지 않게 해뒀습니다**(계약 §2-4 null 불가). 빈 문자열도 마찬가지입니다 — 런타임 503으로 두면 서버는 멀쩡한데 모든 세션 시작이 실패하고 원인 추적이 한참 돌아갑니다
- **막는 범위는 대화 시작뿐**입니다. `/internal/sessions`는 Hume과 무관하게 이미 돌아가니 **1번은 키 없이도 먼저 맞춰볼 수 있습니다**
