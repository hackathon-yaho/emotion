# 정원이 차면 202가 갑니다 — 대기 순번 화면 부탁드립니다 (계약 v1.9 §2-14)

> **상태: ⏳ 회신 대기** (요청 2026-09-05)
> 회신은 `../../response/backend/session-queue.md`에 들어옵니다.
> **막고 있는 작업**: 없습니다. **서버는 기본이 꺼짐**이라 지금 붙이지 않으셔도 동작이 달라지지 않습니다. 다만 **켜는 날 화면이 없으면 6번째 사용자가 아무 설명 없이 실패**합니다.

## 무슨 일이 생기나

**Hume은 동시 접속에 상한이 있습니다.** 요금표 실측값입니다.

| 플랜 | 동시 접속 |
| --- | ---: |
| Free | **1** |
| Starter · Creator | **5** |
| Pro | 10 |

**그리고 상한을 넘긴 연결은 기다리지 않습니다 — 거절당합니다.**

> `E0700` — "You have too many active chats associated with your Hume account. Please close an existing chat session before starting a new one."

**순번도, 예상 대기 시간도, 자리가 났다는 신호도 Hume에서 오지 않습니다.** 그래서 대기열을 서버가 만들었습니다.

## 앱이 할 일 — 202를 갈라 보고, 폴링하고, 취소

### 1. `POST /api/session/start`가 **202**로 올 수 있습니다

```json
201 Created   → 지금까지와 같습니다. 바로 EVI 연결
202 Accepted  → 정원이 찼습니다
{
  "ticketId": "b2f4c1a0-…",
  "position": 3,
  "pollIntervalSec": 2,
  "session": null
}
```

**상태 코드로 가르시면 됩니다.**

### 2. `GET /api/session/queue/{ticketId}`를 `pollIntervalSec` 간격으로

```json
→ { "position": 1, "session": null }
→ { "position": 0, "session": { "sessionId": "…", "humeAccessToken": "…", … } }
```

**`position`이 0인 응답에 세션이 실려 옵니다. 그 응답이 곧 입장권입니다** — `POST /api/session/start`를 다시 부르지 마십시오. 그 `session` 객체는 **§2-4 응답과 같은 모양**이라 그대로 쓰시면 됩니다.

**`position`은 1부터이고 "내가 몇 번째"입니다** — 내 앞에 몇 명이 아닙니다.

### 3. `DELETE /api/session/queue/{ticketId}` — [취소]

**204.** 없는 티켓이어도 204라 실패 처리를 안 하셔도 됩니다.

## 앱이 안 하셔도 되는 것 세 가지

**① 재시도 로직** — 폴링을 계속하시면 됩니다. **자리를 예약해 두지 않으므로** "자리를 받았는데 시간 안에 못 들어갔다" 같은 상태가 없습니다.

**② 순번 계산** — 서버가 줍니다. 앞사람이 이탈하면 다음 폴링에서 저절로 당겨집니다.

**③ 중복 티켓 걱정** — **한 사람에게 티켓 하나**입니다. 대기 중에 `start`를 다시 불러도 **같은 `ticketId`와 같은 순번**이 옵니다. 새로 고침으로 줄이 늘거나 앞당겨지지 않습니다.

## 다만 두 가지는 지켜 주셔야 합니다

**① 폴링을 멈추면 티켓이 만료됩니다(10초).** 브라우저를 닫은 사람이 줄을 영원히 막기 때문입니다. **화면을 벗어나면 `DELETE`를 보내 주시면** 뒷사람이 바로 당겨집니다 — 안 보내셔도 10초 뒤 자동으로 빠집니다.

**만료 뒤 폴링은 404 `QUEUE_TICKET_NOT_FOUND`입니다.** 그때는 **`POST /api/session/start`부터 다시** 하시면 됩니다.

**② `E0700` 폴백** — 서버가 정원을 미리 세므로 **정상 경로에서는 이 오류를 볼 일이 없습니다.** 하지만 우리 카운트와 Hume의 실제 상태가 어긋나는 순간이 있을 수 있고, **조회가 실패하면 서버는 일부러 입장시킵니다**(조회가 죽었다고 대화를 막지 않습니다). 그때 소켓에서 `E0700`이 오면 **`POST /api/session/start`부터 다시** 태워 주십시오 — 그 호출이 202를 주고 줄에 세웁니다.

## 화면에 대해 (요청 아님 — 앱 판단입니다)

- 「앞에 N명」보다 **「N번째로 기다리고 계세요」**가 서버 값과 맞습니다(`position`은 1부터입니다)
- **예상 시간을 서버가 주지 않습니다.** 하드컷이 7분이라 최악을 곱하면 겁주는 숫자가 됩니다 — 안 보여주시는 쪽을 권합니다
- **대기 화면에 갭·valence는 당연히 없습니다**(FR-031)

## 지금 붙이지 않으셔도 됩니다

**`SESSION_QUEUE_ENABLED` 기본값이 `false`**입니다. 꺼진 상태에서는 **202가 나가지 않고 동작이 v1.8과 똑같습니다** — 서버가 Hume에 정원을 묻지도 않습니다.

**켜는 시점은 유료 전환·심사 일정에 맞춰 팀에서 정합니다.** 그때 화면이 준비돼 있으면 좋겠습니다.

## 함께 알려드리는 것 (요청 아님)

- **지금 계정이 무료면 정원이 5가 아니라 1입니다.** 켜는 날 `SESSION_QUEUE_CAPACITY`를 플랜에 맞춰 넣습니다 — 서버 설정이라 앱은 신경 쓰지 않으셔도 됩니다
- **Creator로 올려도 동시 접속은 5로 같습니다.** 늘어나는 건 포함 분수(40 → 200분)뿐입니다
- 정원 판정은 **Hume에 직접 묻습니다**(`chats?status=ACTIVE`). 우리 세션 행을 세지 않는 이유는 **Hume이 비활성 2분에 채팅을 닫는데 우리 행은 30분을 열어 두기 때문**입니다 — 우리 행을 세면 빈 자리를 두고 사람을 돌려보냅니다
