> **상태: ⏳ 회신 대기** (요청 2026-09-03)
> 회신은 `../../response/app/tag-gap-endpoint.md`에 들어옵니다.
> **막고 있는 작업**: S04 추세 화면의 **이야기별 갭 막대**(F9-03, P1). 두 선 그래프(F9-01·02)는 영향받지 않으므로 S04 자체는 진행합니다. 도그푸딩을 막지 않습니다.

## 배경

디자인을 마치고 계약과 대조하다 발견했습니다. **spec F9-03의 출력이 어느 엔드포인트에도 없습니다.**

| 문서 | 내용 |
| --- | --- |
| spec F9-03 출력 | `[{ tag, occurrences, tagAvgGap }]` 상위 N개. 등장 3회 미만 태그는 표시하지 않음 |
| 계약서 §2-8 `GET /api/trend` | `points`(일자별 valence·gap)와 `highlights`(연속 구간)뿐. **태그별 집계가 없습니다** |
| 계약서 §2-6 `GET /api/observations` | 관찰의 `evidence`에 `tag`·`occurrences`·`tagAvgGap`·`userAvgGap`·`ratio`가 있습니다 |

## 관찰의 evidence로 대체할 수 없는 이유

`GET /api/observations`로 일부는 유추됩니다. 그런데 **관찰은 조건을 통과한 태그만 만들어집니다** — 3회 이상 AND 개인 평균의 1.5배 이상(FR-051). 그래서 이 화면에 필요한 것 중 **"3회 이상이지만 1.5배 미만인 태그"가 어디서도 오지 않습니다.**

그 태그들이 이 화면의 핵심입니다. 막대 차트는 **내 평균 실선**과 **×1.5 점선**을 그려놓고 어떤 이야기가 선을 넘었고 어떤 이야기가 못 넘었는지를 보여줍니다 — 넘은 것만 보이면 비교 대상이 없어져 "왜 이게 발견인가"가 설명되지 않습니다. **코드의 판정 기준(FR-051)을 사용자에게 그대로 보여주는 것이 이 화면의 값**이고, 그러려면 탈락한 태그도 필요합니다.

## 제안

경로·필드명은 스케치입니다. `GET /api/trend` 응답에 **필드 하나를 더하는 쪽**을 권합니다 — S04가 이미 그 호출을 하므로 왕복이 늘지 않습니다.

```json
{
  "range": "30d",
  "timezone": "Asia/Seoul",
  "points": [ ... ],
  "highlights": [ ... ],
  "userAvgGap": 0.72,
  "tagGaps": [
    { "tag": "회의", "occurrences": 7, "tagAvgGap": 1.31 },
    { "tag": "주말", "occurrences": 4, "tagAvgGap": 1.16 },
    { "tag": "야근", "occurrences": 4, "tagAvgGap": 0.98 },
    { "tag": "팀장", "occurrences": 3, "tagAvgGap": 0.88 },
    { "tag": "가족", "occurrences": 4, "tagAvgGap": 0.65 }
  ]
}
```

| 항목 | 제안 |
| --- | --- |
| `userAvgGap` | **개인 전체 평균 갭.** 막대의 기준선이라 없으면 그릴 수 없습니다. `×1.5` 판정선은 앱이 이 값으로 계산합니다 |
| `tagGaps` | **등장 3회 이상만** 서버가 걸러 주세요 (F7-03과 같은 기준). 앱이 3회 미만을 숨기는 것보다 서버가 안 주는 쪽이 기준이 한 곳에 남습니다 |
| 정렬 | `tagAvgGap` 내림차순 |
| 개수 | 상위 몇 개까지 줄지 정해 주세요. 화면은 5~7개가 읽기 좋습니다 |
| 기간 | `range`에 종속되는지, 전체 기간 집계인지 알려 주세요. **저는 `range`에 종속되는 쪽이 맞다고 봅니다** — 같은 화면의 두 선 그래프와 기간이 다르면 사용자가 두 그래프를 연결해서 읽을 수 없습니다 |
| 빈 배열 | 3회 이상인 태그가 없으면 `[]`. 앱은 막대 영역을 숨기고 아무 문구도 만들지 않습니다 |

**이미 계산하고 있는 값입니다.** F7-02 태그별 집계와 F7-03 규칙 판정이 배치에서 이미 태그별 평균 갭과 개인 평균을 구합니다(PRD §9.2). 새 계산이 아니라 **이미 있는 숫자를 조회로 열어 주는 것**입니다.

## 결정을 요청하는 것

1. `GET /api/trend`에 필드를 더할지, 별도 엔드포인트로 둘지. **앱은 어느 쪽이든 맞춥니다.**
2. 필드명 확정 (`tagGaps`·`userAvgGap`).
3. 상위 몇 개까지 줄지.
4. `range`에 종속되는지 여부.
5. 3회 미만 필터를 서버가 할지.
