## 배경 — 앱이 위기·갭 신호를 받을 경로가 계약에 없습니다

화면 정의와 계약서를 대조하면서 **P0 기능 두 개가 앱 쪽에서 데이터 경로 없이 남아 있는 것**을 발견했습니다. 원인이 하나라 한 요청으로 묶습니다.

**① S07 위기 안내** — spec F4-04는 담당이 `B/C`이고 처리 ②가 "S07 안내 시트 표시"입니다. 계약서 §5는 S07을 "없음 — 앱 로컬 표시"로 적고 있습니다. 그런데 위기 감지 결과는 AI서버 → 백엔드 `/internal/turns`의 `crisis`로만 흐르고(§3-2), **앱이 그 사실을 알 수 있는 필드가 §2의 12개 엔드포인트 어디에도 없습니다.** 시트를 띄울 트리거가 없는 상태입니다.

**② S02 데모 모드** — F11-01은 대화 화면에 실시간 갭·valence를 노출하라고 합니다. `POST /api/session/start`는 `demoMode` 플래그만 내려주고(§2-4), **턴별 `textValence`·`voiceValence`·`gap`이 앱에 도달하는 경로가 없습니다.** PRD §13 데모 시나리오 1번(같은 문장을 밝은 톤/지친 톤으로 → 갭만 튄다)이 발표의 핵심 장면인데 지금 계약으로는 구현할 수 없습니다.

**누가 틀린 게 아니라 §2가 조회 API 중심으로 짜여 있어서 "대화 진행 중"의 신호가 빠진 것입니다.** 앱은 실시간 경로에서 Hume EVI에 직결되어 우리 서버 응답을 받지 않는 구조(PRD §6)이므로, 이 구간의 신호는 별도로 열어주지 않으면 앱에 닿지 않습니다.

## 다른 경로를 검토한 결과

백엔드에 요청을 넣기 전에 앱 쪽에서 해결할 수 있는지 먼저 봤습니다.

| 경로 | 판정 | 이유 |
| --- | :---: | --- |
| 앱 ↔ AI서버 직접 채널 신설 | ✕ | AI서버에 인바운드 경로·인증을 새로 만들어야 하고, **실시간 응답 경로에 부하를 얹습니다.** PRD §6이 홉을 줄인 이유(NFR-01 p95 2초)를 스스로 훼손합니다 |
| 앱이 로컬에서 판정 (EVI 이벤트의 프로소디 + 키워드 매칭) | △ | 48종 매핑표와 위기 키워드 목록이 **앱과 AI서버 두 곳에 생깁니다.** 어긋나면 §1.4 재현성 지표가 깨집니다. 게다가 **텍스트 valence는 앱이 알 방법이 없어** 데모 모드가 반쪽이 됩니다 |
| AI 응답 텍스트에 메타 태그 동봉 | ✕ | 응답은 Hume TTS를 거치므로 **사용자에게 음성으로 읽힙니다.** 계약서 §4가 명시적으로 금지한 실패 모드입니다 |
| **백엔드 조회 엔드포인트 1개** | **◎** | 백엔드가 `/internal/turns`로 **이미 받고 있는 값**만 되돌려주면 됩니다. 새 계산·새 저장·새 아키텍처가 없습니다 |

## 제안 — `GET /api/session/{sessionId}/live`

경로·필드명은 스케치이고 확정은 백엔드 몫입니다. 요지는 **이미 받은 값을 앱이 대화 중에 읽게 해달라**는 것뿐입니다.

```json
{
  "sessionId": "sess_9c1d4e",
  "lastTurnIndex": 7,
  "crisisDetected": true,
  "turns": [
    { "turnIndex": 7, "textValence": 0.70, "voiceValence": -0.62, "gap": 1.32, "gapTriggered": true }
  ]
}
```

| 항목 | 제안 |
| --- | --- |
| 호출 시점 | **S02 화면에서만.** 대화 종료·화면 이탈 시 중단합니다. 다른 화면은 기존 조회 API를 씁니다 |
| 증분 조회 | `?sinceTurnIndex=` 로 마지막으로 받은 인덱스 이후만 받습니다 |
| **`transcript` 제외** | **발화 텍스트는 넣지 말아 주세요.** 앱은 EVI에서 이미 받고 있어 필요가 없고, 넣으면 노출면만 하나 늘어납니다 |
| `crisisDetected` | **세션 단위 boolean.** turn 단위로 묶지 말아 주세요 — PRD §7이 `crisis_event`에 `turn_id`를 두지 않은 것과 같은 이유입니다. 앱은 `false → true` 전이에서 **한 번만** S07을 띄웁니다 |
| 비데모 계정 | `demoMode == false`면 valence·gap을 `null`로 내리는 것도 방법입니다. 앱은 어차피 S02에 그리지 않지만(FR-031), 서버가 막아주면 방어선이 이중이 됩니다. 백엔드 판단에 맡깁니다 |
| 폴링 간격 | 1~2초를 생각하고 있습니다. **서버가 감당할 값을 알려주세요.** `softWrapSec` 선례처럼 `session/start` 응답에 내려주시면 앱에 상수로 박지 않겠습니다 |

## 함께 부탁하는 것 — 데모 세션의 적재 신뢰도

`/internal/turns`는 fire-and-forget이고 5xx·타임아웃에 **1회만 재시도 후 포기**합니다(§3-2, spec F5-04). 적재가 실패하면 대화는 정상이지만 **앱도 그 턴을 못 봅니다** — 무대에서 데모 배지가 비고, 그 턴의 위기 감지는 S07까지 도달하지 못합니다.

`demoMode` 계정에 한해 재시도를 늘리거나 실패를 눈에 보이게 남겨 주실 수 있는지 알려주세요. **AI서버 몫이라면 AI 담당에게 별도 요청을 내겠습니다** — 어느 쪽인지만 알려주시면 됩니다. (위기 감지 자체는 이 실패와 무관하게 AI서버에서 이미 처리되므로, 안전 기능이 이 경로에 종속되는 것은 아닙니다.)

## 결정을 요청하는 것

1. 엔드포인트 신설에 동의하는지. **백엔드가 선호하는 다른 전달 수단(SSE 구독 등)이 있으면 그쪽으로 맞추겠습니다** — 앱은 폴링이든 스트림이든 됩니다.
2. 경로·필드명 확정.
3. 폴링 간격(또는 스트림 정책)과 그 값을 `session/start`로 내려줄지.
4. 비데모 계정에 valence·gap을 `null`로 막을지.
5. `crisisDetected`를 세션 단위 boolean으로 둘지.
6. 데모 세션 적재 재시도 강화가 백엔드 몫인지 AI서버 몫인지.
