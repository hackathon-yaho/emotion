# 401 응답에 CORS 헤더가 없습니다 — 앱이 인증 실패를 볼 수 없습니다

> **상태: ✅ 회신 완료 (2026-09-06) — 고쳤고 배포됐습니다**
> - 회신: [`../../response/app/cors-on-401.md`](../../response/app/cors-on-401.md)
> - **원인**: `CorsConfig`가 `WebMvcConfigurer`라 **MVC 계층**에서만 붙었는데, `JwtAuthFilter`는 그 앞에서 401을 만들고 끝냈습니다. **"400은 컨트롤러가, 401은 필터가 만든다"는 짐작이 원인 그 자체**였습니다
> - **조치**: `CorsFilter`를 `HIGHEST_PRECEDENCE`로 등록해 인증 필터보다 앞에 뒀습니다. 설정값은 그대로. 배포본에서 401·404·`/internal` 401까지 **전부 헤더가 붙는 것을 확인**했습니다
> - **403·404·500**: 이제 계층과 무관합니다. 다만 **미인증 상태에서는 없는 경로도 401**이고(인증 필터가 `/api/**` 전체를 가로챕니다), §2-11·§2-12의 403은 컨트롤러가 만들어 원래도 붙고 있었습니다 — **앱이 더 손볼 곳은 없습니다**
> - 회귀 테스트 2건 추가(107건 통과). **기존 프리플라이트 테스트 3건은 전부 통과하는 채로 이 결함이 배포돼 있었습니다**
>

## 무엇을 봤나

배포된 서버에 같은 오리진으로 세 가지 응답을 받아 헤더를 비교했습니다 (2026-09-06).

| 요청 | 상태 | `access-control-allow-origin` |
| --- | --- | --- |
| `GET /api/health` | 200 | ✅ `http://localhost:3000` |
| `POST /api/auth/kakao` (빈 본문) | 400 | ✅ `http://localhost:3000` |
| **`GET /api/me` (잘못된 JWT)** | **401** | ❌ **없음** |

401 응답의 헤더 전부입니다 — CORS 헤더가 한 줄도 없습니다.

```
HTTP/2 401
date: ...
content-type: application/json;charset=UTF-8
rndr-id: ...
server: cloudflare
vary: Accept-Encoding
```

**400은 붙고 401은 안 붙는다**는 것이 단서로 보입니다. 400은 컨트롤러가 만들고, 401은 **인증 필터가 컨트롤러 앞에서** 만듭니다 — CORS 필터가 그 뒤에 있거나 인증 실패 경로가 CORS 처리를 타지 않는 것으로 짐작합니다.

## 앱에서 무슨 일이 벌어지나

**브라우저가 응답을 통째로 막습니다.** 앱 코드에는 상태 코드도, 본문의 `error.code`도 오지 않고 **네트워크 실패로만** 보입니다.

결과가 셋입니다.

1. **F1-02가 동작하지 않습니다.** 계약 §1-2의 `TOKEN_EXPIRED`를 보고 로그아웃시키는 경로가 있는데, **그 401이 앱에 도달하지 못하므로 영원히 안 불립니다.** 만료된 사용자는 "서버에 닿지 못했습니다"만 보고 무엇을 해야 할지 모릅니다 — 실제로는 다시 로그인하면 되는 상황입니다
2. **오류 문구가 거짓말을 합니다.** 앱은 원인별로 문구를 가르는데(F2-04·§7-1), 인증 실패가 네트워크 실패로 도착하니 **서버 탓을 사용자 네트워크 탓으로** 말하게 됩니다
3. **진단이 느려집니다.** 오늘 통합에서 이 증상으로 한참 헤맸습니다. 서버는 0.4초로 멀쩡히 응답하는데 앱만 "닿지 못했다"고 하니, 타임아웃·콜드 스타트·캐시를 차례로 의심했습니다

## 부탁드리는 것

**모든 응답에 CORS 헤더가 붙게 해주세요 — 특히 인증 필터가 만드는 401입니다.**

Spring Security라면 보통 `CorsFilter`를 보안 필터 체인 **앞**에 두거나(`http.cors(...)` + `SecurityFilterChain` 순서), `AuthenticationEntryPoint`에서 헤더를 직접 붙이는 방식으로 해결되는 것으로 압니다. **구현 방식은 그쪽이 정하실 일이고**, 저희가 확인하고 싶은 것은 결과 하나입니다.

```sh
curl -s -o /dev/null -D - https://emotion-6yeh.onrender.com/api/me \
  -H "Origin: https://hackathon-yaho.github.io" \
  -H "Authorization: Bearer invalid.jwt" | grep -i access-control
# → access-control-allow-origin 이 나와야 합니다
```

**403·404·500도 같이 확인해 주시면 좋겠습니다.** 401만 문제인지, 필터가 만드는 응답 전부인지에 따라 앱이 F1-02 외에 더 손볼 곳이 생깁니다 — 예를 들어 §2-11·§2-12의 403(타 사용자 세션)도 같은 상태라면, 남의 기록을 열었을 때 앱이 "서버에 닿지 못했다"고 말하게 됩니다.

## 앱은 이렇게 두겠습니다

**앱에서 우회하지 않습니다.** 브라우저가 막은 응답은 앱이 볼 방법이 없어서, 여기서 할 수 있는 일이 없습니다.

다만 문구는 오늘 고쳤습니다 — 종전 "연결이 되지 않습니다. **네트워크를 확인해 주세요**"에서 **"서버에 닿지 못했습니다. 잠시 후 다시 시도해 주세요"** 로요. 사용자 네트워크는 멀쩡한 경우가 대부분인데 그쪽을 보게 만들고 있었습니다.

## 함께 알려드리는 것 (요청 아님)

- **콜드 스타트를 앱 쪽에서 조금 덮었습니다.** 타임아웃을 연결 20초·수신 45초로 올리고 **GET에만 1회 재시도**를 넣었습니다(POST는 안 합니다 — `session/start`를 다시 보내면 세션이 둘 생깁니다). 오늘 실측으로 **17.7초**와 **274초**를 둘 다 봤는데, **앞은 덮이고 뒤는 못 덮습니다.** cron 킵얼라이브가 급하다는 판단(`backend/docs/blocked.md` ⑦)에 저희 실측도 같은 말을 합니다
- 오늘 통합에서 앱 쪽 결함도 넷 잡혔습니다 — 만료된 이어하기에 `resume` 호출, `resumedChatGroupId: null`에 파서가 죽던 것, 뒤로 가기로 나가도 마이크가 안 꺼지던 것, 폴링 타이머가 남던 것. **전부 실서버를 붙여야만 나오는 것들이었습니다**
