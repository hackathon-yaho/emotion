| 1. 엔드포인트 신설 · 전달 수단 | **동의, 폴링.** SSE는 채택하지 않았습니다 — 아래 참조 |
| 2. 경로·필드명 | `GET /api/session/{sessionId}/live`, 제안하신 필드 그대로(`lastTurnIndex`·`crisisDetected`·`turns[]`) |

| 4. 비데모 계정 마스킹 | **`turns: []`로 막습니다. `null`은 쓰지 않습니다.** 아래 참조 |

## 4번 — `null`이 아니라 `turns: []`인 이유

계약서 §1-3이 `null`의 뜻을 이미 "측정하지 못했다"로 못박아뒀습니다. 여기서 마스킹 용도로 `null`을 또 쓰면 **"측정 실패"와 "볼 권한 없음"이 같은 값이 되어** 그 규칙이 오염됩니다. `turns: []`는 §1-3의 "관찰이 조건 미달이면 빈 배열" 선례와 같은 형태라 뜻이 겹치지 않습니다. `crisisDetected`는 데모 여부와 무관하게 항상 정상 값을 내려드립니다 — S07은 모든 사용자에게 떠야 하니까요.

## 6번 — 데모 전용 분기를 두지 않은 이유

말씀하신 위험(데모에서 배지가 비고 S07이 안 뜨는 것)에 동의합니다. 다만 데모 계정만 재시도를 올리는 분기를 만들면, **실사용에서 한 번도 안 돌아본 코드가 무대에서 처음 도는** 상황이 됩니다. 그래서 `/internal/turns` 재시도 전체를 3회로 올렸습니다(§3-2 v1.3). 9/10 도그푸딩에서 실사용으로 이미 검증됩니다.

## 왜 SSE가 아니라 폴링인가

`/internal/turns`(§3-2)는 fire-and-forget이고 실패 시 재시도 후 포기하는 구조입니다 — 즉 턴 데이터가 백엔드에 도착한다는 보장 자체가 없습니다. SSE로 "즉시 푸시"를 만들어도 원천에서 유실된 턴은 밀 게 없어, 폴링 대비 얻는 게 적습니다. 반대로 폴링은 늦게 도착한 턴을 다음 주기에 회수합니다. 서버 상태(연결 보관)도 필요 없어 인스턴스가 늘어도 그대로 갑니다. 1~2초 지연은 S07·데모 오버레이 용도에 충분하다고 판단했습니다.
