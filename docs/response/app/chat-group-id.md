## 결론

**3안입니다. 제안하신 모양 그대로 만들었습니다.**

```
POST /api/session/{sessionId}/chat-group
{ "chatGroupId": "cg_2b7f11" }
→ 204 No Content
```

**소켓이 열려 `chat_metadata`가 오면 그때 바로 보내시면 됩니다.** 2안(종료 시 본문)은 만들지 않았습니다 — 말씀하신 대로 그것 하나로 충분하고, **덮지 못하는 경우가 정확히 이어하기가 필요한 경우**였습니다.

## `resumedChatGroupId`는 **`null`입니다** — 빈 문자열이 아닙니다

물어보신 것에 답합니다. **계약 §1-3에 행으로 못 박았습니다.**

| 상태 | 응답 |
| --- | --- |
| `/chat-group`을 받은 세션 | `"resumedChatGroupId": "cg_2b7f11"` |
| **아직 못 받은 세션** | **`"resumedChatGroupId": null`** |

빈 문자열은 **어떤 경우에도 오지 않습니다.** 빈 값을 막는 자리가 두 군데입니다 — 요청의 `chatGroupId`가 공백뿐이면 **400**이라 애초에 저장되지 않고, 응답은 Jackson이 `null`을 그대로 싣습니다(필드가 사라지지도 않습니다).

**본문에 `"resumedChatGroupId":null` 문자열이 실제로 들어 있는지를 테스트로 고정했습니다.** 나중에 누가 `@JsonInclude(NON_NULL)`을 전역으로 켜면 그 테스트가 깨집니다 — 그때 앱의 방어 코드가 조용히 무의미해지는 것을 막으려는 것입니다.

**지금 하고 계신 빈 문자열 방어는 걷어내셔도 됩니다.**

## 세 가지를 앱이 편한 쪽으로 정했습니다

**① 멱등입니다 — 재연결마다 그냥 보내셔도 됩니다.**

같은 값을 몇 번 보내도 204입니다. **다른 값이 오면 마지막 값이 이깁니다** — 값이 바뀌었다는 것은 새 그룹이 생겼다는 뜻이고, 그러면 이전 그룹에는 이어붙일 맥락이 없기 때문입니다. **재시도 로직을 따로 두지 않으셔도 됩니다.**

**② 종료된 세션에도 204입니다.**

소켓 직후에 보내는 값이라 **도착하기 전에 세션이 닫힐 수 있습니다**(하드컷·다른 탭에서 새 세션 시작). 그걸 404로 튕기면 앱이 재시도해도 영영 성공하지 못합니다. 저장 자체는 해로울 게 없어서 받습니다.

**③ 값을 검사하지 않습니다.**

`cg_` 접두사 같은 것을 확인하지 않습니다. Hume이 준 문자열을 **그대로** 보관했다가 그대로 돌려드립니다. 형식을 검사하면 **Hume이 접두사를 바꾸는 날 우리가 먼저 깨집니다.** 막는 것은 공백(400)과 200자 초과(400) 둘뿐입니다.

| 오류 | 조건 |
| --- | --- |
| 400 `VALIDATION_ERROR` | `chatGroupId`가 없거나 공백뿐, 또는 200자 초과 |
| 403 `FORBIDDEN` | 남의 세션 |
| 404 `SESSION_NOT_FOUND` | 없는 세션 |

## 테스트로 고정한 것

| 확인 | 결과 |
| --- | --- |
| 올린 값이 이어하기 응답으로 되돌아온다 | ✅ |
| 같은 값 2번 + 다른 값 1번 → 마지막 값 | ✅ |
| 안 올린 세션의 `resumedChatGroupId`가 **본문에 `null`** | ✅ |
| 종료된 세션에도 저장된다 | ✅ |
| 남의 세션은 403 | ✅ |
| 공백 문자열은 400 | ✅ |

전체 **90건 통과**입니다.

## 확인 부탁드리는 것 하나

**강제 종료 후 재연결하면 Hume이 같은 `chat_group_id`를 줍니까, 새 값을 줍니까?**

`resumed_chat_group_id`로 붙는 것이니 **같은 값일 것으로 보고 있고, 그 전제로 "마지막 값이 이긴다"를 골랐습니다.** 만약 재연결마다 새 값이 나온다면 그래도 동작은 맞습니다(새 그룹이 실제 맥락을 가지고 있으니까요). **급하지 않습니다** — EVI를 붙이시다 보이면 알려주십시오.
