# `usedSec`은 맞았습니다 — 카드가 가리킨 것은 종료 6초 뒤 앱이 새로 연 빈 세션입니다

> **회신: ✅ 완료 (2026-09-14)** — 계약 **v1.12**
> `../../request/backend/open-session-used-time.md`에 대한 답입니다.
> **원가 상한은 깨져 있지 않았습니다.** 46초 대화는 `user_end`로 정상 종료됐고, 홈 카드가 가리킨 것은 **그 뒤에 생긴 턴 0건 세션**입니다.
> **앱에 부탁이 하나 생겼습니다** — `../../request/app/summary-route-restarts-session.md`

- 회신자: 백엔드
- 대상: 앱
- 관련 문서: `../../02-architecture/api-contract.md` §2-2 (v1.12)

## 실측 — 운영 DB와 Hume 채팅 기록

테스트 계정(`f707c165…`), 2026-09-14 KST입니다.

| 세션 | 시작 → 종료 | 턴 | 서버 `usedSec` | Hume 연결 |
| --- | --- | --- | --- | --- |
| `1b07e2b9` | 20:47:47 → 20:48:57 `user_end` | 6 | 61초 | 68초 |
| `4f9493e8` | **20:49:03** (종료 6초 뒤) | **0** | **0초** | 1초 |
| `39091ea0` | 23:17:09 → 23:19:18 `user_end` | 12 | 118초 | 128초 |
| `b7cab295` | **23:19:25** (종료 7초 뒤) | **0** | **0초** | 연결 없음 · 아직 열려 있음 |

- **46초 대화(`1b07e2b9`, `durationSec` 46)는 이미 닫혀 있어 `openSession`이 될 수 없습니다.** 계산했다면 `usedSec`은 61초였습니다.
- **`/me`가 돌려준 열린 세션은 종료 6초 뒤 생긴 `4f9493e8`입니다.** 턴이 0건이라 `usedSec 0` · `remainingSec 420`이 맞습니다. 새로고침해도 같았던 것도 이것으로 설명됩니다.
- 같은 일이 23:19에 한 번 더 있었습니다(`b7cab295`).

## 짐작하신 부분 — 열린 세션에서 0을 주지 않습니다

`usedSec`은 열린 세션에서도 매번 계산합니다. `SessionService.usedSec()` = **`max(turn_log.occurred_at) − started_at`**, 상한은 `hardCutSec`입니다. `/me`와 이어하기(§2-5-1)가 **같은 함수**를 쓰므로 ③도 같은 값입니다(TC-22 테스트 `resumeGivesRemainingTime`).

## 벽시계(`now − started_at`)로는 바꾸지 않습니다

「Hume은 연결 시간으로 과금한다」는 말은 맞습니다. **하지만 앱이 죽으면 연결도 함께 끊깁니다.** 죽은 뒤 흐른 시간은 과금되지 않으므로, 그 시간을 빼면 원가 상한을 지키는 것이 아니라 **사용자 시간을 뺏는 것**이 됩니다. 2분 말하고 앱이 죽은 뒤 5분 뒤에 이어하면 잔여 시간이 0이 되어 **409로 막힙니다. spec TC-22가 바로 이 경우**이고, 테스트로 묶여 있습니다.

지금 방식에도 **작은 과소 계상은 있습니다.** 위 표에서 보듯 마지막 턴 이후 꼬리가 Hume 연결보다 **7~10초** 적게 잡힙니다. 원가 상한을 뚫을 크기는 아니라 지금은 두겠습니다. **§2-2 표에 `usedSec` 정의를 적었습니다** — 계약서에 「시작부터」만 있어 벽시계로 읽힐 수 있었습니다.

## 백엔드가 바꾼 것 — v1.12

**턴 0건 세션은 `openSession`으로 내주지 않습니다.** 말이 한 번도 오가지 않은 세션은 이어갈 대화가 없는데 「중단된 대화 · 남은 7분」으로 보였습니다. 앱이 09-09에 기록 화면에서 턴 0건을 감추기로 한 기준(`../backend/empty-session-visibility.md` — *"실패의 잔해"*)과 같습니다.

- 앱이 새로 시작하면 `start()`가 그 세션을 닫으므로 남지 않습니다.
- **앱 코드는 바꿀 필요가 없습니다.** `openSession == null`은 이미 처리하고 계십니다.

## 요청하신 회귀 테스트

| 테스트 | 단언 |
| --- | --- |
| `meExposesOpenSession` (고침) | 3분 전 시작, 100초에 턴 → `usedSec 100` · **`remainingSec 320`** (종전에는 턴 없이 `420`을 단언하고 있었습니다) |
| `meHidesOpenSessionWithoutTurns` (신규) | 턴 0건 열린 세션 → `openSession` 없음 |
| `resumeGivesRemainingTime` (기존, TC-22) | 2분 말하고 5분 뒤 이어하기 → `remainingSec 300` |

말씀하신 「시작 → n초 뒤 → `remainingSec < hardCutSec`」은 **턴이 없으면 실패하는 것이 정상**이라 턴을 넣은 형태로 만들었습니다. 백엔드 테스트 110건 통과.

## 곁다리 — 끝낸 세션이 잠깐 열려 있음

**복제 지연은 아닙니다.** Supabase에는 읽기 복제본이 없고, `POST /end`는 트랜잭션을 커밋한 뒤 응답합니다. **본문과 같은 원인일 가능성이 큽니다** — 카드가 끝낸 세션이 아니라 새로 생긴 빈 세션이었을 것입니다. 다만 「새로고침하면 사라졌다」는 이것으로 설명되지 않아서, 앱 요청 문서 ③에 `sessionId` 확인을 부탁드렸습니다.

넣으신 `endedSessionIdProvider` 필터는 해롭지 않으니 두셔도 됩니다. 원인이 같다면 v1.12가 같은 역할을 하므로 없애셔도 됩니다.
