## 붙인 것

| 계약 | 앱 |
| --- | --- |
| §2-4가 **202**를 낼 수 있다 | `POST /api/session/start`를 **상태 코드로 가릅니다** — 200이면 세션, 202면 티켓. 본문 모양으로 짐작하지 않습니다 |
| `GET /api/session/queue/{ticketId}` | `pollIntervalSec` 간격으로 폴링. **앱에 상수로 박지 않았습니다** |
| `position == 0` → `session`이 입장권 | 그 자리에서 세션으로 넘어갑니다 |
| `DELETE .../queue/{ticketId}` | 「기다리기 그만두기」 버튼 |
| 404 = 만료·남의 티켓 | **조용히 §2-4부터 다시 시작합니다.** 사용자에게 알릴 것이 없습니다 |

화면은 링을 작고 흐리게 둔 **기다림 상태**입니다 — "기다리고 있습니다 / N번째로 기다리고 있습니다 · 자리가 나면 바로 시작됩니다". 순번은 **1부터**라는 것 그대로 따랐습니다.

## `E0700` 이어하기 예외 — 개정에서 짚어주신 것

> `start`로 되돌리면 중단된 세션이 닫혀 **이어할 대화가 사라집니다.**

**이게 앱에서 제일 위험한 분기였습니다.** 소켓 오류를 한 덩어리로 묶어 두면 "실패했으니 다시 시작"이 자연스러운 처리라 그대로 짰을 겁니다.

EVI 실패에 **`busy`를 따로 만들었습니다.**

- `slug`에 `E0700`이 있거나 **문구에 "too many active chats"가 있으면** busy입니다 — 슬러그는 바뀔 수 있어 문구도 같이 봅니다(테스트 2건)
- busy면 **3초 뒤 `_open()`을 다시 탑니다.** `_open()`은 `me().openSession`을 먼저 보므로 **이어하기 중이었으면 다시 이어하기로** 들어갑니다 — 새 세션을 만들지 않습니다
- 그동안 화면에는 **"이어할 대화는 그대로 있습니다 · 잠시 뒤 다시 연결합니다"** 가 뜹니다. 사용자가 "사라졌나" 하고 새로 시작하지 않도록 문장으로 붙잡아 둡니다

## 폴링을 멈추면 티켓이 만료된다는 것

화면을 벗어나면 타이머를 정리합니다. **브라우저를 닫으면 폴링이 끊기고 서버가 티켓을 만료시킨다**는 설계 그대로이며, 앱이 따로 할 일은 없다고 봤습니다 — `beforeunload`로 `DELETE`를 쏘는 것은 신뢰할 수 없는 경로라 넣지 않았습니다.

## 지금 확인할 수 없는 것

**서버 기본이 꺼짐이라 202를 실제로 받아본 적이 없습니다.** 지금까지의 검증은 계약 본문 기준의 단위 테스트뿐입니다(티켓 파싱·`position` 의미·`pollIntervalSec` 기본값 2·`E0700` 분기).

**켜실 때 알려주시면 같이 확인하겠습니다.** 특히 이 둘을 눈으로 보고 싶습니다.

1. **202 → 폴링 → `position: 0` → 입장**까지 한 번
2. **줄이 서 있을 때 신규 시작도 202**라는 것 (새치기 방어)

## 함께 알려드리는 것 (요청 아님)

- **지금 배포본은 샘플 모드라 대기열을 타지 않습니다** (`response/backend/backend-deployed-rebuild.md`). 라이브로 켜는 날 함께 확인하겠습니다
- 샘플 모드에서는 **줄을 서지 않습니다.** 대기열은 Hume 동시 접속 상한 때문에 있는 것인데 샘플은 Hume에 붙지 않습니다 — 화면만 보시려면 S02의 상태 전환용 프로토타입 화면(`?picker=1`)에서 「대기열」을 고르시면 됩니다
