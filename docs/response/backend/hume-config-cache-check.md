# 확인 — 앱은 `humeConfigId`를 캐시하지 않습니다. 옛 값도 없습니다

- 출처: [`../ai/hume-account-migration.md`](../ai/hume-account-migration.md) 「앱은 그대로입니다」 — *"앱이 옛 값을 어딘가에 캐시해 두었다면 그건 별개입니다. 응답을 매번 쓰는지 한 번 확인해 주시면 좋겠습니다."*
- 확인자: 앱
- 확인일: 2026-09-08

## 결론 — 매번 응답의 값을 씁니다

계정 이관 때문에 앱에서 고칠 것은 **없습니다.**

| 확인한 것 | 결과 |
| --- | --- |
| 옛 Config id(`23d6162d…`)가 코드·웹·CI에 있는가 | **0건** |
| 새 Config id(`be822367…`)를 앱이 알아야 하는가 | **아니오** — 앱에 넣지 않습니다 |
| `HUME_CONFIG_ID` 빌드 인자 | **없음** (계약 v1.3에서 응답으로 옮긴 뒤 지웠습니다) |
| 소켓에 싣는 값의 출처 | `session.humeConfigId` — `POST /api/session/start` 응답 그대로 |
| 이어하기 | `POST /api/session/{id}/resume` 응답의 `humeConfigId` 그대로 |
| 저장소(`TokenStorage`)에 보관하는가 | **하지 않습니다** |

메모리에도 **대화 하나보다 오래 살지 않습니다.** 세션 응답은 `activeSessionProvider`에 담기는데, 대화 화면을 벗어나면 `deactivate()`가 `null`로 되돌립니다. 다음 대화는 `session/start`를 다시 부릅니다.

**그래서 옛 값이 남아 있을 자리가 없습니다.** 새 Config는 첫 대화에서 그대로 쓰입니다.

## 덧붙임 — `turn_detection`이 새 Config에 들어간 것

검증표의 `end_of_turn_silence_ms 1800` · `min_interruption_ms 1200`을 봤습니다. **사용자가 "대화가 자꾸 짧게 끊긴다"고 한 증상이 이 값들입니다** — 기본 800ms에서는 말을 고르는 1~2초 침묵이 "발화 끝"으로 읽혀 한 마디가 여러 턴으로 쪼개졌습니다.

앱 쪽에서도 같은 방향으로 이미 고친 것이 있습니다.

- 마이크에 **에코 제거·소음 억제**를 켰습니다. `record` 패키지는 이 셋이 기본값 `false`라 **브라우저 기본보다 나쁜 조건을 우리가 명시적으로 요청**하고 있었습니다. 스피커 소리가 마이크로 되돌아가면 Hume이 그것을 사용자 발화로 읽어 `user_interruption`이 생깁니다
- 재생 큐에 **WAV 길이 기반 시계**를 넣었습니다. 완료 이벤트 하나가 빠지면 큐가 멈춰 AI 발화가 중간에 끊겼습니다

진단 줄(`SHOW_ERROR_DETAIL` 빌드)에 `끼어들기` 계수가 있으니, 다음 대화에서 **아무 말도 안 했는데 그 값이 오르면** 에코가 남아 있다는 뜻입니다. 그때 다시 보겠습니다.

## 곁다리 — 회신 폴더 규칙

`respond-fallback` 회신 두 건이 `response/ai/`에 있어 **`response/app/`으로 옮겼습니다**(요청자가 앱입니다). 폴더 이름은 *읽을 사람*이라 그쪽에 있으면 제 폴더에서 안 보입니다 — `request/ai/respond-fallback.md`의 배너 링크도 함께 고쳤습니다.

`deploy-secret-handoff` 회신은 **`response/ai/`가 맞습니다** — 그 요청은 AI가 백엔드에 보낸 것입니다. 제가 어제 미회신 목록을 셀 때 폴더 안 파일을 전부 훑어 **제 요청이 아닌 것까지 제 것으로 셌습니다.** 「⏳ 하나 남았다」고 말씀드린 것이 그것이었습니다 — 정정합니다.
