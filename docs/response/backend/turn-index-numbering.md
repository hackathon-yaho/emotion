## 결론

**세 가지 다 확인했고, 3번은 계약에 한 줄 넣었습니다.**

| 확인 요청 | 답 |
| --- | --- |
| 1. `turnIndex`를 어디에 들고 있나 | **세션 캐시(프로세스 메모리)에 든다. 다만 0에서 시작하지 않고 `lastTurnIndex`에서 시작한다** — 재시작하면 캐시가 비고, 캐시가 비면 조회를 다시 하므로 **재시작이 곧 재시드**다 |
| 2. 이어하기 때 캐시를 버리고 다시 부를 수 있나 | **부릅니다.** 다만 "이어하기"라는 사건이 AI서버에는 보이지 않아서, **유휴 간격으로 감지**합니다 (아래) |
| 3. `occurredAt`이 발화 시각이 맞나 | **맞습니다.** 재시도 3회는 **문자열까지 동일한 값**을 보내고, **밀리초 정밀도**로 찍습니다. 같은 세션에서 두 발화가 같은 값을 갖지 않도록 하는 장치도 넣었습니다 |

**가드가 뚫리는 경로는 없습니다.** 3번이 그 가드의 전제인데, 아래 설계가 그 전제를 코드로 강제합니다.

---

## 1. `turnIndex`는 메모리에 들지만 0에서 시작하지 않습니다

채번식이 이렇습니다.

```
turnIndex = lastTurnIndex(조회 시점 값) + 그 조회 이후 내가 발급한 개수
```

`lastTurnIndex`는 §3-4 조회 응답에서 받습니다. 세션 캐시 엔트리 안에 조회 결과와 같이 들어가므로, **캐시가 살아 있는 동안만 메모리 카운터가 의미를 갖고, 캐시가 죽으면 카운터도 같이 죽습니다.**

그래서 재시작이 위험 경로가 아닙니다.

| 상황 | 캐시 | 다음 CLM 요청에서 벌어지는 일 |
| --- | --- | --- |
| AI서버 재시작 | 비어 있음 | §3-4를 **다시 조회** → 그 시점 `lastTurnIndex`에서 이어 붙임 |
| 배포·스케일 아웃으로 다른 인스턴스에 붙음 | 그 인스턴스엔 없음 | 위와 동일 |
| 세션 진행 중 (정상) | 있음 | 메모리 카운터 +1 |

**"프로세스 메모리라 재시작에 사라지고 그때 0부터 시작한다"는 경로가 설계상 존재하지 않습니다.** 0이 되는 유일한 경우는 백엔드가 `lastTurnIndex: 0`을 준 경우, 즉 실제로 적재된 턴이 없을 때입니다.

**한 번에 2개를 발급합니다.** 한 번의 주고받기에서 user 턴과 assistant 턴이 둘 다 적재되는데(파이프라인 ⑦), assistant 턴은 스트림이 끝난 뒤에 나갑니다. 번호는 **user 턴을 처리하는 시점에 둘 다 미리 잡아둡니다**(user = n+1, assistant = n+2). 스트림이 길어져도 순서가 뒤집히지 않습니다.

## 2. 이어하기 감지 — 유휴 간격으로 합니다

**AI서버에는 재연결이 보이지 않습니다.** Hume은 턴마다 상태 없는 HTTP 요청을 보내고 거기 실려 오는 것은 `custom_session_id`뿐입니다. "지금이 재연결 직후"라는 신호가 요청 어디에도 없습니다.

그래서 **간접 신호**를 씁니다. 이어하기는 사용자가 대화를 떠났다가 돌아오는 것이므로 **턴 사이에 반드시 긴 공백**이 생깁니다.

```
같은 sid의 직전 턴으로부터 AI_SESSION_REFETCH_IDLE_SEC(초기 60초) 이상 지났으면
  → 캐시를 버리고 §3-4를 다시 조회 → lastTurnIndex 재시드
```

**틀려도 손해가 없는 방향으로 잡았습니다.** 사용자가 대화 중간에 60초를 그냥 침묵해도 이 조건에 걸리는데, 그때 벌어지는 일은 **불필요한 조회 1회**뿐입니다. 재조회는 같은 값을 돌려주고 카운터는 그대로입니다. 반대로 놓치면 인덱스가 어긋나므로, **거짓 양성은 싸고 거짓 음성은 비쌉니다.**

보조로 하나 더 봅니다. Hume이 매 요청에 이력 전체를 실어 보내므로, **들어온 이력의 user 메시지 수가 내 카운터보다 많으면** 그것도 재조회 신호로 씁니다. 이어하기 때 Hume이 복원한 이력을 실어 주는지는 아직 실측하지 않았으므로 **주 신호가 아니라 보조**로만 둡니다.

**그리고 이 두 장치가 다 실패해도 유실은 안 납니다** — 그때는 `occurredAt`이 다르므로 백엔드 가드의 "충돌" 가지를 타서 `max+1`로 저장됩니다. 즉 3번이 이 전체의 마지막 안전망입니다.

## 3. `occurredAt` — 발화 시각이 맞고, 계약에 명시했습니다

**세 가지를 보장합니다.**

**① 재시도는 항상 같은 값입니다.** 페이로드를 만들 때 한 번 찍고, 그 **문자열 그대로**를 재시도에 다시 보냅니다. 재시도 경로에서 시각을 다시 찍는 코드가 없습니다 — 적재 시각·전송 시각을 쓰지 않습니다. 테스트로 고정합니다(같은 턴을 3회 재시도시켜 `occurredAt`이 동일한지 검사).

**② 밀리초 정밀도로 찍습니다.** `2026-09-18T12:31:02.417Z` 형식입니다. 계약 §3-2 예시가 초 단위였어서 **v1.5로 예시와 규칙을 같이 고쳤습니다.**

**③ 같은 세션의 서로 다른 발화는 값이 겹치지 않습니다.** 한 세션의 턴은 순차 처리되고 사이에 LLM 호출이 끼므로 실제로 같은 밀리초에 두 발화가 들어올 수 없습니다. 그래도 가드가 이 필드 하나에 걸려 있으니 **방어 규칙을 넣습니다** — 새로 찍은 값이 같은 세션 직전 턴과 같으면 1ms를 더합니다. 이러면 "다르다 → 충돌" 가지가 오판할 여지가 사라집니다.

**어느 시계로 찍는지는 알려드립니다.** Hume이 메시지마다 `time{begin,end}`를 주지만 기준점을 실측하지 않았으므로, **AI서버가 자기 UTC 시계로** 찍습니다. user 턴은 분석이 끝난 직후(수신에서 약 0.4초), assistant 턴은 스트림 종료 시점입니다. **정확한 발성 시각이 아니라 수백 ms 뒤**입니다 — 가드의 목적(재시도와 충돌 구분)에는 영향이 없지만, 나중에 이 값으로 발화 간격을 분석하실 거라면 이 오차를 알고 쓰셔야 합니다. 필요하시면 Hume `time`을 실측해 교체하겠습니다.

## 계약 변경 (v1.5)

§3-2 필드 표에 `occurredAt` 행을 넣고 예시를 밀리초로 고쳤습니다. **필드 추가·삭제는 없습니다.**

> `occurredAt` — **발화 시각.** RFC 3339, **밀리초 정밀도**(`2026-09-18T12:31:02.417Z`). 적재 시각·전송 시각이 아니다. **재시도는 최초 시도와 완전히 같은 값을 보낸다** — 백엔드가 `unique (session_id, turn_index)` 충돌을 "재시도"와 "다른 발화"로 가르는 기준이 이 필드다. 같은 세션에서 서로 다른 발화가 같은 값을 갖지 않는다
