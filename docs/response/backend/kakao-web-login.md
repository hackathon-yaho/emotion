# 회신 — 웹 카카오 로그인은 인가 코드 방식입니다 (SDK 소스로 확정)

- 원본 요청: [`../../request/app/kakao-web-login.md`](../../request/app/kakao-web-login.md) (백엔드 → 앱, 2026-09-04)
- 회신자: 앱
- 회신일: 2026-09-04
- 확인 방법: `kakao_flutter_sdk_user`/`_auth` **2.0.1을 실제로 내려받아 소스를 읽었습니다.** 문서 인용이 아니라 구현입니다

---

## 결론

**인가 코드 방식으로 갑니다. 계약 §2-1 개정안 그대로 확정합니다.**

문서에 쓰신 것보다 상황이 한 단계 더 강했습니다.

| 백엔드 추정 | 실제 (SDK 2.0.1 소스) |
| --- | --- |
| 웹은 "인가 코드만 발급"된다 | **웹에서는 로그인 API 자체가 없습니다.** `loginWithKakaoAccount()`·`loginWithKakaoTalk()`·`loginWithKakao()`·`loginWithNewScopes()`·`issueAccessToken()`이 전부 `kIsWeb`에서 `KakaoClientException(notSupported)`를 던집니다 |
| `authorize()`가 인가 코드를 돌려준다 | **반환값으로도 안 옵니다.** 웹 구현은 `window.location.href = url`로 페이지를 통째로 넘기고 **`Future.value('')`** 를 돌려줍니다 (`auth_platform_web.dart`) |

즉 웹에서 SDK가 하는 일은 **인가 URL 조립 + 리다이렉트**뿐이고, 그 뒤는 전부 앱이 직접 짭니다. 그래서 **웹 경로에는 카카오 SDK 의존성을 넣지 않습니다** — 확인용으로 붙였다가 뺐습니다(22개 패키지가 따라옵니다). URL 조립 몇 줄이 SDK 전체보다 읽기 쉽고, 웹에서 던지는 API를 실수로 부를 위험도 없습니다.

## 계약 §2-1 — 개정안 확정

제안하신 형태 그대로입니다.

```json
POST /api/auth/kakao
{ "kakaoAuthCode": "abcd...", "redirectUri": "http://localhost:3000/" }
```

- **`redirectUri`를 앱이 같이 보냅니다.** 로컬과 배포가 다르다는 지적 그대로입니다
- **서버가 등록 목록과 대조해 거절하는 것도 동의합니다.** 열어두면 남의 주소로 인가 코드를 흘릴 수 있는 자리라는 판단에 이견 없습니다
- **`codeVerifier`(PKCE)는 넣지 않습니다.** SDK에서도 선택 인자이고, 넣으면 리다이렉트를 건너 검증자를 보관했다가 서버로 넘겨야 해서 **필드가 하나 더 늘어납니다.** 코드 교환에 서버의 클라이언트 시크릿이 필요하니 코드 단독으로는 교환되지 않습니다. **나중에 넣기로 하면 §2-1에 `codeVerifier` 한 칸을 추가하면 됩니다**
- **응답은 그대로** — `token`·`expiresAt`·`profileId`·`isNewUser`
- **`app_id` 대조가 필요 없어지는 것도 맞습니다.** 우리 서버 키로 교환한 토큰은 정의상 우리 앱 것입니다

계약서 개정은 **백엔드가 해 주십시오**(개정안을 그쪽에서 쓰셨고, `POST /api/auth/kakao`는 백엔드 소유입니다). v1.6이 올라오면 앱이 그 필드로 맞춥니다.

## 확인 부탁 — `client_id`가 인가와 교환에서 갈립니다

**여기가 유일하게 제가 실측으로 닫지 못한 지점입니다.**

SDK 웹 구현은 인가 URL의 `client_id`에 **`KakaoSdk.appKey`(웹에서는 JavaScript 키)** 를 넣습니다.

```dart
final params = <String, String>{
  Constants.clientId: KakaoSdk.appKey,   // 웹 = JavaScript 키
  ...
```

그런데 백엔드는 **REST 키 + 시크릿으로 교환**하실 계획입니다. 카카오가 **JS 키로 발급된 인가 코드를 REST 키로 교환하는 것을 받아주는지**를 저는 키가 없어 확인할 수 없습니다.

**그래서 인가 URL도 REST 키로 만드는 쪽을 권합니다.**

```
https://kauth.kakao.com/oauth/authorize
  ?client_id={REST_API_KEY}&redirect_uri={등록된 주소}&response_type=code
```

- **카카오가 문서화한 "REST API로 카카오 로그인" 웹 흐름 그대로**입니다. 특별한 걸 하는 게 아닙니다
- **`client_id`가 인가·교환 양쪽에서 같아져** 위 질문 자체가 사라집니다
- **REST 키는 URL에 실리는 값이고, 시크릿은 서버에만 남습니다.** 보호는 시크릿과 Redirect URI 화이트리스트가 합니다
- 어차피 SDK 웹 경로를 안 쓰니 **URL을 우리가 만드는 데 비용이 없습니다**

이러면 **앱에 필요한 키가 JavaScript 키가 아니라 REST API 키**가 됩니다 — 아래 "키 전달" 항목에 영향이 있습니다.

**혼용이 된다고 확인해 주시면 JS 키로 그대로 갑니다.** 백엔드는 이미 실계정으로 교환을 돌려보셨으니 확인이 빠를 것 같습니다. 둘 중 어느 쪽이든 **Redirect URI 등록값은 그대로 유효합니다.**

## Redirect URI · 포트 — 등록해 주신 값 그대로 갑니다

| 항목 | 값 | 앱 |
| --- | --- | --- |
| 플랫폼(Web) 사이트 도메인 | `https://hackathon-yaho.github.io` | **맞습니다** |
| Redirect URI (배포) | `https://hackathon-yaho.github.io/emotion/` | 확정 |
| Redirect URI (로컬) | `http://localhost:3000/` | 확정 — **`flutter run -d chrome --web-port=3000`으로 고정합니다.** `app/README.md`에 적었습니다 |
| 경로 전략 | **해시 라우팅 유지.** path 전략으로 바꿀 계획 없습니다 | 확정 — `404.html`도 필요 없습니다 |

앱 루트로 받는 판단도 맞습니다. 카카오는 `http://localhost:3000/?code=...`처럼 **프래그먼트 없이** 돌려주고, 해시 경로는 그 뒤에 앱이 직접 붙입니다.

**CORS 회신의 "포트 고정하지 마세요"와 충돌하는 것처럼 보이는데, 이유가 다릅니다.** CORS는 `localhost:*`로 열려 있어 고정이 필요 없고, **카카오 Redirect URI는 문자열 완전 일치라 고정이 필요합니다.** 그래서 3000으로 띄우되, 그 이유가 CORS가 아니라 카카오라는 것을 README에 남겼습니다 — "포트가 다르면 로그인만 실패한다"는 지적 그대로입니다.

## 앱이 짜야 하는 흐름 (참고 — 계약과 무관)

`authorize()`가 값을 안 돌려주므로 **리다이렉트 복귀를 앱이 받아야** 합니다.

```
① S00에서 "카카오로 시작하기" → 인가 URL로 페이지 이동
② 카카오 동의 → 등록된 Redirect URI로 복귀 (?code=...)
③ 앱 시작 시 Uri.base의 code를 읽어 POST /api/auth/kakao
④ JWT 저장 → 게이트 통과 → 홈
⑤ 주소창의 ?code= 를 지운다 (history.replaceState)
```

**⑤를 빼먹으면 새로고침 때 쓴 코드를 다시 보냅니다** — 인가 코드는 1회용이라 400이 됩니다. 이건 앱 쪽 함정이라 여기 적어만 둡니다.

## ⚠️ F10-03 — 인가 코드 방식이면 **앱이 unlink를 할 수 없습니다**

**요청 3번(탈퇴 시 카카오 연결 해제를 앱이 맡아 달라)이 이 결정과 함께 성립하지 않게 됩니다.**

근거로 쓰신 문장이 이것이었습니다.

> 앱은 그 시점에 본인 액세스 토큰이 있어 자기 계정만 끊습니다

**인가 코드 방식에서는 그 전제가 깨집니다.** 코드는 서버로 넘어가고, 카카오 액세스 토큰은 **백엔드만** 손에 쥡니다. 앱에는 우리 JWT뿐이라 `/v1/user/unlink`를 부를 자격증명이 없습니다. 탈퇴 시점에 카카오 로그인을 한 번 더 통과시키면 얻을 수는 있지만, **"탈퇴하려는 사람에게 다시 로그인을 시키는"** 흐름이 됩니다.

**제안 — 백엔드가 사용자 토큰으로 unlink 하시는 게 맞아 보입니다.**

```
① 앱이 DELETE /api/account
② 백엔드가 10개 테이블 삭제
③ 백엔드가 카카오 unlink (사용자 액세스 토큰으로)
④ 204
```

- **Admin 키가 필요 없습니다.** 제가 아는 한 `POST /v1/user/unlink`는 **사용자 액세스 토큰(Bearer)** 으로도 동작합니다 — Admin 키는 `target_id`로 남을 끊을 때 쓰는 방식입니다. **"Admin 키를 서버에 두지 않는다"는 결정을 지키면서 서버가 unlink할 수 있습니다.** 이 점만 확인 부탁드립니다
- **②→③ 순서는 그대로 지켜집니다.** 사용자 데이터가 먼저 사라지고, ③이 실패해도 탈퇴는 성립합니다 — 실패를 응답에 섞지 말고 로그만 남기시면 앱은 그대로 성공 처리합니다
- **다만 저장할 것이 생깁니다** — 로그인 때 받은 카카오 액세스 토큰은 유효기간이 짧아 탈퇴 시점엔 만료돼 있을 테니, **리프레시 토큰을 보관**해야 합니다. 새 비밀이 하나 늘어나는 셈이라 **결정은 백엔드 몫**입니다
- **보관이 싫으시면** 앱이 탈퇴 직전에 카카오 재인가를 받아 토큰을 얻는 방법이 남습니다. 되기는 하는데 **탈퇴 흐름에 동의 화면이 한 번 더 끼는** 걸 감수해야 해서, 저는 위쪽을 권합니다

**F10-03은 Phase 6이라 지금 막히는 건 없습니다.** 다만 계약 §2-1을 고치실 때 같이 정하는 편이 낫습니다 — 같은 결정에서 파생된 항목이라서요.

## 동의항목 — 회원번호만으로 확정합니다

**화면에 사용자 이름을 쓰는 곳이 없습니다.** 구현된 11개 화면 전부를 `nickname`·이름류 표현으로 훑었고 하나도 없습니다. S01이 쓰는 건 날짜뿐입니다.

- 닉네임·프로필 사진·이메일 **전부 비활성 유지**에 동의합니다
- "나중에 열면 기존 사용자 재동의"라는 조건도 확인했습니다. **여는 쪽으로 바꿀 계획 없습니다**
- 동의 화면이 짧아 첫 화면 이탈이 줄어든다는 판단에도 동의합니다 — S00의 고지 3줄과 성격이 맞습니다

## 키 전달 — 값을 문서·저장소·대화에 붙이지 마세요

**전달이 아예 필요 없는 경로를 권합니다.**

- **repo variable은 팀장님이 직접 등록해 주세요.** 저장소 관리자시니 Settings → Secrets and variables → Actions → Variables에서 바로 넣으실 수 있고, **그러면 값이 저에게 올 필요가 없습니다.** 배포 빌드는 그 값만 있으면 됩니다
- **변수명은 위 `client_id` 결정 뒤에 확정합시다.** REST 키로 가면 `KAKAO_JS_KEY` → `KAKAO_REST_KEY`로 바뀌고, 워크플로(`app-web.yml`)와 `core/config/env.dart`도 같이 고쳐야 합니다. **등록을 두 번 하지 않으려면 결정이 먼저입니다**
- **로컬 테스트용 값만** 팀 사설 채널(카카오톡 DM 등)로 주시면 됩니다. `--dart-define`으로만 쓰고 저장소에 넣지 않습니다

## 백엔드 실계정 검증, 도움이 됐습니다

`POST /api/auth/kakao` → `GET /api/me` 왕복과 TC-01(재로그인 동일 `profileId`)이 이미 확인된 상태라, **앱이 확인할 범위가 "인가 코드를 받아 요청을 조립하는 것"으로 줄었습니다.** 실패하면 볼 곳이 앱 쪽 한 군데뿐입니다.

`app_id` 대조 미검증 항목은 위 결정대로 가면 **필요 자체가 없어집니다.**

## 정리 — 백엔드가 확인해 주실 것 두 개

1. **`client_id` 혼용 가능 여부** (JS 키로 인가 → REST 키로 교환). 안 되면 인가 URL도 REST 키로 갑니다. **키 변수명이 여기에 달려 있습니다**
2. **`/v1/user/unlink`가 사용자 액세스 토큰으로 되는지** + 리프레시 토큰 보관 여부. F10-03의 담당이 앱에서 백엔드로 넘어가는 건이라 결정이 필요합니다

계약 §2-1 개정과 Redirect URI 등록값은 **더 확인할 것 없이 확정**입니다.
