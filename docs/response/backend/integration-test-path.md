## 1. 터널 방식에 동의합니다 — 한 PC에 합치지 않는 이유

**합치면 검증하려던 것이 사라집니다.** 통합 테스트에서 확인하려는 건 "코드가 맞물리나"만이 아니라 **"네트워크 너머에서도 맞물리나"** 입니다. 같은 PC의 `localhost`끼리 붙이면 지연이 사실상 0이고 끊김이 없어서, 실제 배포에서 처음 만날 문제들이 통과합니다. 특히 아래 두 개는 로컬 합체로는 절대 안 나옵니다.

- **`GET /internal/sessions` 타임아웃.** 지금 `AI_SESSION_LOOKUP_TIMEOUT_MS=800`인데, 이건 같은 데이터센터를 가정한 값입니다. **터널 두 개를 거치면 왕복이 이걸 넘길 수 있고, 넘기면 fail-closed라 대화가 401로 막힙니다.**
- **터널이 끊겼을 때의 동작.** 무료 ngrok은 재시작 때 URL이 바뀌고 세션도 끊깁니다. 그때 우리 실패 처리가 실제로 도는지 봐야 합니다.

또 실무적으로, 제 PC에 백엔드를 띄우려면 JDK·Gradle과 **Supabase 접속 정보**가 제 쪽으로 와야 합니다. 시크릿을 옮기지 않는 편이 낫습니다.

### 통합 기간에 조정하는 값 (`.env`로만, 코드 변경 없음)

| 값 | 평시 | 통합 중 | 이유 |
| --- | --- | --- | --- |
| `AI_SESSION_LOOKUP_TIMEOUT_MS` | 800 | **2000** | 터널 2개 왕복. 첫 턴에만 도는 호출이라 대화 지연 예산(NFR-01)에 미치는 영향이 제한적입니다 |
| `AI_SESSION_LOOKUP_CONNECT_RETRY` | 1 | 1 | **연결 단계 실패에만** 1회 재시도합니다. 4xx·5xx 응답은 재시도하지 않습니다 — 터널 재시작 순간의 연결 거부와 백엔드의 실제 거절은 다릅니다 |

**fail-closed는 통합 중에도 끄지 않습니다.** 조회가 안 되면 401로 막는 동작(§3-4)을 개발 편의로 우회하는 스위치를 두면, 그 스위치가 배포까지 따라갈 위험이 있습니다. 대신 위 두 값으로 여유를 줍니다.

## 2. AI서버 준비 시점 — 9/6

붙일 수 있는 상태의 기준을 이렇게 잡았습니다.

| 날짜 | AI서버 상태 |
| --- | --- |
| 9/5 | `app/rules/` 순수 함수 + 단위 테스트 (valence·gap·crisis·tags·guard). 네트워크 없음 |
| **9/6** | **`GET /internal/sessions` 호출부 + 세션 캐시 + `POST /chat/completions`(SSE) + `POST /internal/turns` 적재.** 이때부터 붙일 수 있습니다 |
| 이후 | `POST /internal/observations`·`/internal/summaries` 수신부 |

**밀리면 이 문서에 날짜를 고쳐 적겠습니다.** 백엔드 Phase 2·3이 먼저 서면 그쪽 일정에 맞추겠습니다.

**터널 열기 전에 먼저 할 수 있는 게 있습니다.** 제가 보낼 요청과 기대하는 응답을 **고정 JSON으로 저장소에 올리겠습니다**(`ai-server/eval/fixtures/internal/`). 백엔드는 그걸로 `curl` 검증을 미리 할 수 있고, 저는 같은 파일로 목을 만듭니다. **같은 파일을 양쪽이 쓰면 "제 쪽에선 되는데요"가 안 생깁니다.**

## 3. 순서 — `GET /internal/sessions`부터, 동의합니다

이유가 하나 더 있습니다. **이 호출은 CLM 인증이면서 동시에 `lastTurnIndex` 공급원**입니다(§3-4, `turn-index-numbering.md` 회신). 이게 안 서면 `/internal/turns`를 붙여도 **번호가 맞는지 검증할 수 없습니다.**

제안하는 순서입니다.

1. `GET /internal/sessions/{id}` — 200·404·타임아웃 3종. **404가 401로 바뀌는지**까지 봅니다
2. `POST /internal/turns` — user·assistant 각 1건, 그리고 **같은 턴 재전송**으로 202 중복 판정 확인
3. `POST /internal/summaries` — 백엔드 → AI서버 방향 (제 터널)
4. `POST /internal/observations` — 같은 방향

2번에서 **재시도 시나리오를 일부러 만들어 보는 것**을 제안합니다. 백엔드에서 응답만 버리시면(저장은 성공, 202를 안 보냄) 제가 재시도하고, 그때 `occurredAt`이 같아서 중복으로 판정되는지가 확인됩니다. **그 가드가 실제로 도는 걸 한 번은 봐야** 합니다.

## 알려주신 것 — 전부 반영했습니다

| 항목 | 조치 |
| --- | --- |
| `BACKEND_BASE_URL`이 8000인데 백엔드는 8080 | **`http://localhost:8080`으로 고쳤습니다.** 지적 맞습니다 |
| `AI_TURN_POST_RETRIES`가 아직 1 | **3으로 올렸습니다.** 지수 백오프(200ms·600ms·1800ms), 전 세션 동일 적용 |
| `X-Internal-Secret` 별도 경로 전달 | 알겠습니다. 받으면 제 `.env`에만 넣습니다. **저장소에 넣지 않습니다** |
| PRD §12 개정 (9/10은 목표) | 확인했습니다. 아래에 영향 정리 |

### PRD §12 개정이 AI 쪽에 미치는 영향

제가 `session-context-lookup.md`에 "9/10 도그푸딩은 고정 임계값으로도 성립합니다"라고 쓴 건 **날짜가 고정이라는 전제**였습니다. 지금은 이렇게 바뀝니다.

**고정 임계값으로 시작하는 판단 자체는 그대로 유효합니다.** 오히려 근거가 강해졌습니다 — 도그푸딩을 일찍 시작할수록 20쌍 스냅샷이 빨리 모이고, 임계값은 그 데이터가 있어야 정할 수 있습니다(ai-pipeline §4.3). **임계값을 정하려고 도그푸딩을 미루면 순서가 거꾸로입니다.**

바뀐 건 **제 쪽 마감 압박의 성격**입니다. 9/10이 목표가 되면서 "그날까지 임계값이 없어도 된다"가 아니라 **"임계값 없이도 데이터가 쌓이게 만들어 두는 것"이 더 중요**해졌습니다. `.env` 폴백 임계값과 조회값 우선 규칙이 그 대비입니다.

## 함께 알려드리는 것 (요청 아님) — Hume 계정과 결제가 갈리면 막힙니다

**⚠️ Hume 콘솔 Config를 만드는 계정과 결제하는 계정이 같아야 합니다.**

지금 두 가지가 서로 다른 담당으로 나뉘어 있습니다.

| 항목 | 담당 | 출처 |
| --- | --- | --- |
| Hume Config 생성·소유 (`config_id` 발급) | **AI** | `response/app/hume-config-id.md` |
| Hume 플랜 확인·결제 | **백엔드** | PRD §14-3 |

`config_id`는 **그 Config가 만들어진 워크스페이스에 묶입니다.** 제가 제 계정에서 Config를 만들고 백엔드가 다른 계정에서 결제하면, 결제한 쿼터는 제 `config_id`에 적용되지 않습니다. **대화는 붙는데 5분 만에 끊기고, 원인이 코드로 보이지 않습니다.**

**계정 하나를 팀 공용으로 쓰고, 거기서 Config 생성과 결제를 모두 하는 것**을 제안합니다. 누구 계정으로 할지는 결제 주체이신 쪽에서 정해 주시면, 제가 그 계정에 접근해 Config를 만들겠습니다.

**그리고 무료 티어로는 통합 테스트도 못 합니다.** Free는 월 5분에 **동시 접속 1**입니다(2026-09-04 요금 페이지 확인). 세션 하드 컷이 7분이라 **한 세션이 월 할당량보다 깁니다.** Starter는 월 40분에 동시 접속 5인데, 3인이 동시에 말해 보는 상황이 동시 접속 1에서는 성립하지 않습니다. **동시 접속 수는 PRD §11에 없던 항목이라 §14-3 행에 추가해 두었습니다.**
