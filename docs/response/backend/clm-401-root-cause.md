# 1.5초로 끊기는 원인을 찾았습니다 — `custom_session_id`가 CLM까지 안 옵니다

> **회신: ✅ 원인 확정 (2026-09-07)**
> `backend/docs/blocked.md` ①의 **"턴이 0건이다 — CLM 호출이 1.5초 만에 죽는다"**에 대한 답입니다.
> **CLM 요청·응답 형식 문제가 아닙니다.** 요청이 **인증 정보 없이** 옵니다.
> 고칠 곳은 앱 한 줄입니다 — 요청했습니다(`../../request/app/custom-session-id-not-reaching-clm.md` ⏳). **백엔드 후속 작업은 없습니다.**

- 회신자: AI
- 대상: 백엔드
- 관련 문서: `backend/docs/blocked.md` ① · `../../02-architecture/api-contract.md` §4

---

## 결론

앱이 `custom_session_id`를 **소켓 URL의 쿼리 파라미터**로 넘기는데, **Hume은 그 경로로 받지 않습니다.** 그래서 Hume이 우리 CLM을 부를 때 `?custom_session_id=`가 **아예 붙지 않고**, AI서버는 계약 §4대로 401을 냅니다. EVI는 CLM이 401을 주면 그 자리에서 대화를 접습니다 — 그게 **1.5초**입니다.

Hume이 값을 받는 경로는 **`session_settings` 메시지**입니다. 앱은 이미 그 메시지를 보내고 있어서, 필드 하나만 얹으면 됩니다.

## 근거 — Cloud Run 요청 로그

`voice_session` 11·12번, Hume 채팅 목록의 1.5초짜리들과 **시각이 그대로 맞습니다.**

```
16:19:53Z  POST 401  0.0027s  .../chat/completions      ← 쿼리 없음
16:20:08Z  POST 401  0.0019s  .../chat/completions
16:20:29Z  POST 401  0.0026s  .../chat/completions
16:21:12Z  POST 401  0.0020s  .../chat/completions
16:24:19Z  POST 401  0.0025s  .../chat/completions
   … 같은 것 5건 더 (16:24~16:28) …
```

**2ms입니다.** 백엔드에 세션을 물어보러 가지도 못했습니다. 지목하신 세 후보 중 남는 것이 없습니다.

| 후보 | 판정 |
| --- | --- |
| 시크릿 불일치 | **아닙니다** — 백엔드까지 가지도 않았습니다 |
| 요청 모양이 파서 가정과 다르다 | **아닙니다** — 본문을 읽기 전에 끝났습니다 |
| SSE 응답 형식이 안 맞는다 | **아닙니다** — 응답을 만들지도 않았습니다 |

## 정정 — 제가 남긴 "요청 뼈대"는 Hume이 보낸 게 아니었습니다

`blocked.md`가 기대하신 "첫 요청의 뼈대"가 로그에 있긴 한데, **읽어 보니 Hume이 아니었습니다.**

```
POST 401  .../chat/completions?custom_session_id=00000000-0000-4000-8000-000000000000
{ "messages": [ {"content": "str(2)", "role": "str(4)"} ], "stream": "bool" }
```

전부 이 값 하나이고, `00000000-…-000000000000`은 **제가 `request/backend/deploy-secret-handoff.md`에 예시로 적어 둔 값**입니다. 메시지 1건에 본문 2글자짜리 — 손으로 찌른 탐침입니다. `/internal/summaries`·`/internal/observations` 401 탐침도 같은 시각대에 있습니다.

**그래서 우리는 아직 Hume의 실제 요청을 한 번도 못 봤습니다.** 제 로그 도구가 이걸 "Hume이 실제로 보낸 요청의 모양"이라고 단정해서 라벨을 붙이고 있었고, 저부터 그렇게 읽었습니다. 라벨을 고쳤습니다.

## 제 쪽에서 고친 것 — **401이 로그에 안 남고 있었습니다**

**열 번의 실패 동안 AI서버 구조화 로그가 통째로 비어 있었습니다.** `custom_session_id`가 없을 때 로그 한 줄 없이 401을 던지고 있었고, 그래서 원인을 우리 로그가 아니라 Cloud Run 요청 로그에서 찾았습니다. **안 보이는 실패는 없는 실패와 구별되지 않습니다.**

두 가지를 고쳐 배포했습니다.

1. **이 401도 이유 코드와 함께 로그에 남깁니다** — `clm_unauthorized:missing_custom_session_id`
2. **요청 본문의 모양을 인증보다도, 스키마 검증보다도 먼저 남깁니다** — 401이나 400으로 끝나도 모양은 건집니다. 무료 5분이라 같은 요청을 다시 부를 기회가 많지 않습니다

회귀 테스트로 묶었습니다(`tests/test_e2e.py`, 242건 통과).

## 다음에 갈리는 지점

앱이 고친 빌드를 올리고 **한 번만** 걸면 로그가 셋 중 하나를 냅니다.

| 로그 | 뜻 |
| --- | --- |
| `clm_unauthorized:missing_custom_session_id` | 아직 안 실렸다 |
| `clm_unauthorized:session_not_found` | **실렸다.** 여기부터는 백엔드 조회 문제 |
| `turn` | 통과 |

**두 번째가 나오면 그때 백엔드를 부르겠습니다.** 그전까지 백엔드가 할 일은 없습니다.

## 분수

**약 1.3분을 썼고 3.7분 남았습니다.** 지금 상태로는 몇 번을 걸어도 1.5초씩 태우기만 합니다. 앱 수정 전까지는 대화를 걸지 않는 편이 좋겠습니다.
