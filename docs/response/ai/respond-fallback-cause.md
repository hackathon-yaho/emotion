# 원인 확정 — Gemini 무료 티어 **429**입니다. 그리고 재시도가 그 한도를 스스로 키우고 있었습니다

- 앞선 회신: [`respond-fallback.md`](respond-fallback.md) — 태그 판정과 계측 추가
- 회신자: AI
- 회신일: 2026-09-07

## 결론

**의심 1(무료 티어 분당 한도)이 맞았습니다.** 계측을 넣고 대화 한 번을 걸자 로그가 바로 말했습니다.

```
07:19:49  error    model=gemini-3.8-flash reason=llm_rate_limited
07:19:49  error    reason=respond_failed:RateLimitError:429
07:19:49  respond  respondTtftMs=2106 respondTotalMs=2106 turnIndex=2
```

**12턴 중 10턴이 429입니다.** 성공한 2턴은 TTFT가 3.9초·4.8초로 느렸는데, 그것도 재시도를 거쳐 겨우 살아난 턴입니다.

## 그런데 재시도가 문제를 키우고 있었습니다

**OpenAI SDK는 429에 기본 2회 재시도합니다.** 그래서 **429 한 번이 요청 3건**이 됩니다.

| | 우리가 생각한 것 | 실제 |
| --- | --- | --- |
| 응답 호출 | 6 RPM | **18 RPM** |

**한도를 우리가 스스로 만들고 있었습니다.** 한 턴이 429를 맞으면 그 턴의 재시도가 다음 턴을 429로 밀어 넣고, 그게 또 재시도를 낳습니다. 세션이 길수록 실패율이 오르던 모양(7턴 중 1회 → 16턴 중 15회)이 이것으로 설명됩니다.

**제가 앞선 회신에서 "5초 간격 연속 12회 전부 성공"이라고 적었는데, 그 시험은 실패가 없어서 재시도도 없었습니다.** 실사용의 증폭을 재현하지 못한 시험이었습니다.

## 고친 것

**① SDK 자동 재시도를 껐습니다** (`max_retries=0`, 응답 경로만).

같은 키로 같은 모델을 다시 부르는 것은 **한도에 걸린 조합을 다시 부르는 것**이라 요청 수만 늘립니다. 빠르게 실패하고 넘어가는 편이 사용자에게도 빠릅니다.

**② 429면 정형 문장 대신 다른 조합으로 갈아탑니다.**

```
1칸  기본 키 · gemini-3.8-flash        ← 품질 우선
2칸  여벌 키 · gemini-3.8-flash        ← 키가 있으면 좋은 모델 유지
3칸  기본 키 · gemini-3.5-flash-lite   ← 키가 다 걸리면 가벼운 모델로
      ↓ 여기까지 다 막히면 그때 정형 문장
```

**`gemini-3.5-flash-lite`에는 여유가 있습니다** — 분석 호출이 같은 모델로 36턴 전부 성공했습니다. **정형 문장보다 가벼운 모델이 낫습니다.**

**③ 여벌 키를 받을 자리를 만들었습니다** — `GOOGLE_API_KEY_2`·`GOOGLE_API_KEY_3`. 비면 안 씁니다.

테스트 251건 통과, 배포했습니다.

## 남은 것 — **키가 근본 해법입니다**

**무료 티어 한도는 키마다 따로 셉니다.** 지금은 키 하나로 세 사람 몫을 돌리고 있습니다.

사다리는 **한 턴을 살리는 장치**이지 용량을 늘리지 않습니다. 대화가 길어지면 `flash-lite`도 결국 같은 벽에 닿습니다 — 분석이 매 턴 그 모델을 쓰고 있어서, 응답까지 내려오면 둘이 한 한도를 나눠 씁니다.

**팀원 두 분이 각자 키를 하나씩 내주시면 그대로 세 배가 됩니다.** [aistudio.google.com/apikey](https://aistudio.google.com/apikey) 에서 발급되고, 카드 등록 없이 무료 티어로 만들어집니다. 값은 저에게 보내지 마시고 팀장님께 주시면 됩니다 — 서버에 넣는 경로는 이미 있습니다.

## 앱이 제안하신 것에 대한 답 (갱신)

**① 429일 때 잠깐 쉬었다 재시도** — **하지 않기로 했습니다.** 재시도가 원인의 절반이었습니다. 같은 조합을 다시 부르는 대신 **다른 조합으로 갈아탑니다.** 사용자에게는 「생각 중」이 조금 길어지는 것으로 보이는 것은 같고, 앱은 고칠 것이 없습니다.

**② 분석 호출을 갭이 필요한 턴에만** — 앞서 적은 대로 순서를 바꿀 수 없습니다. 다만 **분석과 응답이 이제 같은 모델을 나눠 쓸 수 있게 됐으므로**(3칸), 키가 늘기 전까지는 분석 캐시가 더 중요해졌습니다. 이미 있습니다(`_analyze_cache`).

## 남아 있는 관찰 — 턴이 잘게 끊깁니다

**2분 동안 assistant 턴이 12번**이었습니다. 평균 10초에 한 번입니다.

한도와 별개로 **대화 경험 자체에 영향이 있습니다.** 사용자가 "계속 끊기는 느낌"이라고 했고, 턴이 잘게 쪼개지면 (a) 호출이 그만큼 늘어 한도를 더 빨리 먹고 (b) AI가 말을 짧게 자주 끊어 넣습니다.

**Hume이 발화 종료를 언제 확정하는지에 달린 문제**로 보입니다. 429가 정리된 뒤에 따로 보겠습니다 — **지금 Config를 만지면 무료 분수를 시험에 쓰게 됩니다.** 남은 것이 약 3분입니다.
