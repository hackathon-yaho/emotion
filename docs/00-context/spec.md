# 3. 기능별 상세 명세

## F1 · 계정 · 세션

### F1-01 카카오 로그인

| 항목 | 내용 |
| --- | --- |
| 설명 | 카카오 소셜 로그인 1종으로 가입·로그인한다. 다른 인증 수단은 제공하지 않는다 |
| 트리거 | S00에서 `[카카오로 시작하기]` |
| 입력 | 카카오 SDK가 반환한 액세스 토큰 |
| 처리 | ① 앱이 카카오 SDK로 로그인 ② 액세스 토큰을 `POST /api/auth/kakao`로 전송 ③ 백엔드가 카카오 API로 토큰 검증 ④ 신규면 `account` + `profile` + `account_profile` 생성 ⑤ 자체 JWT 발급 |
| 출력 | `{ jwt, profileId, isNewUser }` |
| 예외 | 토큰 검증 실패 → 401, 재로그인 유도 / 카카오 API 장애 → 안내 후 재시도 |
| 수용 기준 | 재로그인 시 동일 `profileId`가 반환되어 이전 감정 로그가 그대로 조회된다 |
| 연관 | F1-02, F1-04, F10-03 |

### F1-02 JWT 세션 유지

| 항목 | 내용 |
| --- | --- |
| 설명 | 로그인 이후 모든 API 요청을 자체 JWT로 인증한다 |
| 처리 | `Authorization: Bearer <jwt>` 헤더. 만료 시 앱이 카카오 재로그인으로 갱신 |
| 출력 | 인증된 요청의 `profileId` 컨텍스트 |
| 예외 | 만료 → 401 반환. 앱은 대화 중이면 **대화를 끊지 않고** 다음 요청부터 갱신 |
| 수용 기준 | JWT 없이 감정 데이터 API 호출 시 전부 401 |
| 연관 | F1-01 |

### F1-03 로그아웃

| 항목 | 내용 |
| --- | --- |
| 설명 | 기기에서 JWT와 카카오 세션을 폐기한다. **서버 데이터는 삭제하지 않는다** |
| 처리 | 앱 로컬 저장소 정리 + 카카오 SDK 로그아웃 |
| 수용 기준 | 재로그인 시 이전 데이터가 그대로 조회된다 (탈퇴와 구분됨) |
| 연관 | F1-04 |

### F1-04 탈퇴

| 항목 | 내용 |
| --- | --- |
| 설명 | 계정과 모든 감정 데이터를 **즉시 전량 삭제**한다. 유예 기간을 두지 않는다 |
| 트리거 | S06 `[탈퇴]` → 확인 다이얼로그 |
| 처리 | `DELETE /api/account` → F10-03 실행 |
| 출력 | 204. 앱은 S00으로 복귀 |
| 예외 | 부분 삭제 실패 시 **트랜잭션 롤백** 후 오류 반환. "일부만 지워진 상태"를 만들지 않는다 |
| 수용 기준 | 탈퇴 후 같은 카카오 계정으로 재가입하면 **신규 사용자로 시작**한다 |
| 연관 | F10-03 |

### F1-05 온보딩 고지

| 항목 | 내용 |
| --- | --- |
| 설명 | 최초 진입 시 서비스 성격과 데이터 정책을 고지한다 |
| 표시 내용 | ① **"전문 상담·치료를 대체하지 않습니다"** ② **"목소리는 분석 직후 삭제되며 저장하지 않습니다"** ③ 힘들 때 연락할 곳: **자살예방 상담전화 109(24시간)** |
| 처리 | 최초 1회 전체 노출, 이후 S06 설정에서 재열람 |
| 수용 기준 | 로그인 전에 노출되어, 동의 없이 대화 화면으로 진입할 수 없다 |
| 근거 | PRD §10 규제 리스크 · [보건복지부 109 안내](https://www.mohw.go.kr/board.es?mid=a10503010100&bid=0027&act=view&list_no=1479607) |

## F2 · 음성 대화

### F2-01 대화 세션 시작 · 단기 토큰 발급

| 항목 | 내용 |
| --- | --- |
| 설명 | 대화 시작 시 세션 레코드를 만들고 **Hume 단기 액세스 토큰**을 발급한다 |
| 트리거 | S01 홈에서 `[오늘 이야기하기]` |
| 입력 | JWT |
| 처리 | ① `voice_session` 생성 ② `user_baseline.session_count` 조회 → **임계 모드 결정(F3-04)** ③ Hume 액세스 토큰 발급 ④ 반환 |
| 출력 | `{ sessionId, humeAccessToken, humeTokenExpiresAt, thresholdMode, gapThreshold, softWrapSec, hardCutSec, demoMode }` — 전체 스키마는 [api-contract.md](../02-architecture/api-contract.md) §2-4 |
| 예외 | Hume 토큰 발급 실패 → 대화 시작 차단 + 원인 안내 |
| 수용 기준 | **Hume API 키가 앱 번들·네트워크 응답 어디에도 노출되지 않는다** |
| 연관 | F2-02, F3-04, F11-01 |
| 근거 | PRD FR-013 / NFR-04 |

### F2-02 EVI 실시간 연결

| 항목 | 내용 |
| --- | --- |
| 설명 | 앱이 Hume EVI에 연결해 끊김 없는 음성 대화를 수행한다 |
| 처리 | ① 마이크 권한 확인 ② EVI SDK 연결(`custom_session_id = sessionId`) ③ 음성 스트림 송수신 |
| 출력 | 실시간 음성 응답 |
| 예외 | F2-04 |
| 수용 기준 | 사용자가 말하는 도중 앱이 개입하지 않으며, 응답 지연 p95 2초 이내(NFR-01) |
| 연관 | F2-03, F2-04 |
| 개발 주의 | **Flutter · 웹 1순위**(PRD §14-4). 웹에서는 `record`+`audioplayers` 순수 Dart 경로를 타고(`kIsWeb` 분기), 녹음은 PCM16 48kHz 모노에 `echoCancel`·`noiseSuppress`·`autoGain`이 `getUserMedia` 제약으로 전달된다. **마이크는 HTTPS(또는 localhost)에서만 열린다.** 공식 예제는 `access_token`·`config_id`만 넘기므로 **`custom_session_id`는 우리가 쿼리에 추가**한다. 또한 예제는 연결·마이크 실패에서 처리되지 않은 예외를 던지므로 **F2-04 경로는 새로 작성한다**(실측 확인, 2026-09-03) — [Flutter 예제](https://github.com/HumeAI/hume-api-examples/blob/main/evi/evi-flutter/README.md) |

### F2-03 세션 길이 제어

| 항목 | 내용 |
| --- | --- |
| 설명 | 5분에 마무리를 유도하고 7분에 자동 종료한다 |
| 처리 | ① 경과 5분 → AI 프롬프트에 **마무리 유도 지시** 주입 (예: "오늘은 여기까지 정리해볼까요?") ② 경과 7분 → 앱이 연결 종료 후 S02-1로 이동 |
| 출력 | 종료 사유 `soft_wrap` / `hard_cut` / `user_end` |
| 예외 | 하드 컷 직전 사용자가 발화 중이면 **해당 발화가 끝난 뒤** 종료한다. 말하는 중간에 자르지 않는다 |
| 수용 기준 | 7분 초과 세션이 생성되지 않는다. 세션당 원가 상한 $0.49가 지켜진다 |
| 연관 | F2-05 |
| 근거 | PRD FR-011 / NFR-06 — EVI 분당 과금이라 세션 길이가 곧 원가. 하드 컷만 두면 털어놓는 도중 잘려 재방문이 끊긴다 |

### F2-04 연결 · 권한 실패 처리

| 항목 | 내용 |
| --- | --- |
| 설명 | 마이크 권한 거부·네트워크 실패·EVI 장애를 구분해 안내한다 |
| 처리 | 원인별 분기 — ① 권한 거부: 설정 이동 안내 ② 네트워크: 재시도 버튼 ③ EVI 장애: 잠시 후 재시도 안내 |
| 예외 | **어떤 경우에도 앱이 멈추거나 흰 화면이 되지 않는다** |
| 수용 기준 | 비행기 모드에서 대화를 시도해도 앱이 정상 상태를 유지한다 |
| 근거 | PRD FR-012 / NFR-08 |

### F2-06 미종료 세션 자동 정리

| 항목 | 내용 |
| --- | --- |
| 설명 | 앱 강제 종료·네트워크 끊김·배터리 방전 등으로 종료 호출이 없었던 세션을 서버가 정리한다 |
| 트리거 | 스케줄러 주기 실행 (**F11-02 헬스체크와 동일 스케줄러에 태운다** — 추가 인프라 0) |
| 처리 | 시작 후 **30분** 경과한 미종료 세션 → `end_reason: "timeout"`으로 종료 + **배치 큐 적재** |
| 부수 효과 | 새 세션 시작(F2-01) 시 그 사용자의 열린 세션을 먼저 닫는다 → **동시 세션 문제 동시 해결** |
| 수용 기준 | 대화 중 앱을 강제 종료해도 **그 대화가 관찰 집계에 반영된다** |
| 왜 P0인가 | 이게 없으면 중단된 대화가 `voice_session` 열린 채 남아 **배치가 영영 돌지 않는다.** 도그푸딩 10일 중 하루만 이래도 발표에 쓸 데이터가 줄어든다 |
| 연관 | F2-07, F7-01, F11-02 |

### F2-07 중단 세션 이어하기 (P1)

| 항목 | 내용 |
| --- | --- |
| 설명 | 중단된 세션이 있으면 **이전 대화 맥락을 복원해** 이어서 대화한다 |
| 트리거 | 홈(S01) 진입 시 `GET /api/me`의 `openSession`이 `null`이 아님 |
| 처리 | ① "이어서 이야기할까요?" 제안 ② 예 → `POST /api/session/{id}/resume` ③ 응답의 `resumedChatGroupId`를 EVI 핸드셰이크 `resumed_chat_group_id`로 전달 ④ 아니오 → `POST /api/session/{id}/end`로 닫음 |
| 시간 예산 | **남은 시간 = `hardCutSec − usedSec`.** 새 7분을 주지 않는다 — 이어하기로 **세션당 원가 상한 $0.49가 뚫리면 안 된다**(PRD NFR-06) |
| 이어하기 창 | 중단 후 **30분.** F2-06의 정리 시간과 같은 값으로 맞춰 규칙을 하나로 유지 |
| 예외 | 창 경과·잔여 시간 0 → 409 `SESSION_NOT_RESUMABLE`. 앱은 새 세션을 시작한다 |
| 수용 기준 | 이어한 대화에서 AI가 **앞서 나눈 내용을 기억한다** |
| 외부 근거 | Hume Chat Group으로 맥락이 보존된다 — [Resuming Chats](https://dev.hume.ai/docs/speech-to-speech-evi/features/resume-chats) |
| 왜 P1인가 | 없어도 F2-06이 데이터를 지킨다. 밀리면 이것부터 버린다 |

## F3 · 감정 측정

### F3-01 음성 valence 산출

| 항목 | 내용 |
| --- | --- |
| 설명 | 프로소디 48종 점수를 **단일 축 valence(−1~+1)** 로 환산한다 |
| 입력 | `messages[].models.prosody.scores` |
| 처리 | `Σ(긍정 감정 가중치 × 점수) − Σ(부정 감정 가중치 × 점수)` → 정규화 |
| 출력 | `voiceValence: number \| null` |
| 예외 | 점수 누락 → `null`. 갭 미산출(F3-06) |
| 수용 기준 | **동일 입력에 항상 동일 값**을 반환한다(결정적). 동일 음성 3회 반복 시 편차 ±0.1 이내 |
| 미확정 | **48종 → ±1 매핑표는 착수 전 확정 항목**(PRD §14-1). 임의 값을 코드에 넣지 않는다 |
| 근거 | PRD FR-020 · 단일 축으로 줄이는 이유는 ① 두 채널을 같은 척도로 맞춰야 뺄셈이 성립하고 ② "말은 +0.7인데 목소리는 −0.4"가 48종 나열보다 설명력이 높기 때문 |

### F3-02 텍스트 valence 수신

| 항목 | 내용 |
| --- | --- |
| 설명 | 대화 응답 LLM 호출의 **첫 줄**로 텍스트 valence를 함께 받는다 |
| 처리 | ① 시스템 프롬프트가 `<v>{-1.0~1.0}</v>` + 줄바꿈 + 응답 본문 형식을 지시 ② AI서버가 스트림 앞부분을 버퍼링해 파싱 ③ `<v>` 구간을 **제거한 뒤** Hume에 전달 |
| 출력 | `textValence: number \| null` |
| 예외 | 형식 불일치 → `null` (F3-06) |
| 수용 기준 | 사용자에게 `<v>` 태그가 **절대 음성으로 읽히지 않는다** |
| 근거 | PRD FR-021 · 별도 LLM 호출을 추가하면 그 지연이 실시간 경로에 그대로 더해진다. 첫 줄 동봉은 추가 지연이 토큰 몇 개 수준 |

### F3-03 갭 계산

| 항목 | 내용 |
| --- | --- |
| 설명 | `gap = |textValence − voiceValence|` |
| 처리 | 두 값이 모두 존재할 때만 계산 |
| 출력 | `gap: number \| null`, `gapTriggered: boolean` |
| 예외 | 어느 한쪽이 `null`이면 `gap = null`, `gapTriggered = false` |
| 수용 기준 | 같은 문장을 밝은 톤 / 지친 톤으로 말했을 때 **갭 방향이 기대와 일치**한다(20쌍 90% 이상) |

### F3-04 임계값 모드 결정

| 항목 | 내용 |
| --- | --- |
| 설명 | 세션 누적 수에 따라 고정 임계값과 개인 baseline 중 하나를 고른다 |

| 출력 | `thresholdMode: "fixed" \| "personal"`, 적용 임계값 |
| 수용 기준 | 첫 세션부터 갭 트리거가 동작하며(데모 성립), 5회째 세션에서 모드가 `personal`로 전환된 로그가 남는다 |
| 근거 | PRD FR-023 · 고정 단독은 목소리가 원래 낮은 사용자에게 매번 오탐. 개인 baseline 단독은 **첫 사용자에게 baseline이 없어 데모 첫 장면이 작동하지 않는다**. 5회는 도그푸딩 기간(9/10~9/20) 안에 전환 로그를 확보할 수 있는 값 |
| 미확정 | 고정 임계값의 초기 수치는 20쌍 세트 측정 후 결정(PRD §14-5) |

## F4 · 대화 트리거 · 안전

### F4-01 갭 초과 시 되묻기

| 항목 | 내용 |

| 설명 | 갭이 임계를 넘으면 AI가 먼저 되묻는다 |
| 처리 | 갭 초과 신호를 프롬프트에 주입 → LLM이 되묻는 응답 생성 (예: *"괜찮다고 하시는데 목소리는 좀 다르네요. 무슨 일 있으셨어요?"*) |

| 설명 | `turn_log.transcript`를 암호화해 저장한다 |
| 이유 | evidence 열람(F7-07)에 필요하다. 원문을 못 열면 "근거 있는 관찰"이 말뿐이 된다 |
| 수용 기준 | DB를 직접 조회해도 평문 발화가 보이지 않는다 |
| 근거 | PRD FR-042 / §5.1 |

### F5-03 음성 원본 폐기 보장

| 항목 | 내용 |
| --- | --- |
| 설명 | 음성 파일을 우리 서버가 **수신하지도 저장하지도 않는다** |
| 처리 | 음성 원본은 앱 ↔ Hume 구간에만 존재. AI서버는 텍스트와 점수만 받는다 |
| 수용 기준 | 백엔드·AI서버·스토리지 어디에도 오디오 파일이 생성되지 않는다 |
| 근거 | PRD FR-041 · 갭 계산이 끝나면 원본은 쓸 데가 없고, 저장하면 용량·암호화·유출 리스크만 늘어난다 |

### F5-04 전송 실패 처리

| 항목 | 내용 |
| --- | --- |
| 설명 | 로그 적재 실패가 대화를 막지 않는다 |

## F7 · 패턴 발견

### F7-01 배치 트리거

| 수용 기준 | 배치 실패가 대화·조회 기능에 영향을 주지 않는다 |

### F7-02 태그별 집계

| 항목 | 내용 |
| --- | --- |
| 설명 | 사용자 전체 기간의 태그별 갭·valence를 집계한다 |
| 처리 | 태그별 등장 횟수, 평균 갭 / 개인 전체 평균 갭 산출 |
| 출력 | `{ tag, occurrences, tagAvgGap, userAvgGap, ratio }` |
| 예외 | 갭이 `null`인 턴은 제외 |

### F7-03 규칙 판정

| 항목 | 내용 |
| --- | --- |
| 설명 | 관찰을 만들지 말지를 **코드가** 결정한다 |
| 조건 | `occurrences >= 3` **AND** `tagAvgGap >= userAvgGap × 1.5` |
| 미달 시 | **아무 관찰도 만들지 않는다.** 억지로 통찰을 생성하지 않는다 |
| 수용 기준 | 데이터가 부족한 사용자에게 관찰이 생성되지 않는다 |
| 근거 | PRD FR-051·052 · LLM에 로그를 통째로 주면 그럴듯한 패턴을 반드시 만들어낸다. 판정을 규칙으로 고정해야 모든 관찰이 숫자로 역추적된다. 매일 통찰을 뱉는 앱은 신뢰를 잃는다 — 침묵할 수 있어야 말할 때 믿긴다 |

### F7-04 관찰 문장 생성

| 항목 | 내용 |
| --- | --- |
| 설명 | 통과한 집계 결과를 **한 문장으로 표현**한다 |
| 입력 | F7-02의 숫자만 |
| 처리 | LLM에 숫자를 전달해 문장화. 프롬프트 조항 7(숫자 변경 금지·사실 추가 금지) 적용 |
| 출력 | `sentence` (예: *"회의 얘기를 하실 때만 목소리가 유독 무거워지시네요."*) |
| 금지 | **패턴의 존재 여부·강도를 LLM이 판정하지 않는다.** 표현만 담당 |
| 근거 | PRD FR-054 |

### F7-05 evidence 부착

| 항목 | 내용 |
| --- | --- |
| 설명 | 관찰마다 근거 숫자와 근거 turn 목록을 붙인다 |
| 출력 | `evidence: { tag, occurrences, tagAvgGap, userAvgGap, ratio }` + `observation_evidence` 테이블에 근거 turn 연결. **API 응답의 `evidence` 객체에는 turn ID를 넣지 않고**, 근거 대화는 F7-07 상세 조회의 `turns` 배열로만 내려간다 ([api-contract.md](../02-architecture/api-contract.md) §2-6·2-7) |

| 근거 | PRD FR-053 · evidence가 없으면 "근거 있는 관찰"이 주장에 그친다 |

| 항목 | 내용 |

### F7-07 관찰 근거 열람

| 항목 | 내용 |
| --- | --- |
| 설명 | 관찰의 근거가 된 **실제 대화로 내려간다** |
| API | `GET /api/observations/{id}/evidence` |
| 출력 | 근거 turn의 발화 텍스트·시각·갭 |
| 예외 | 근거 turn이 삭제된 경우 → 해당 관찰은 F10-02로 이미 무효화되어 조회되지 않는다 |
| 수용 기준 | 관찰 카드에서 근거 대화 N건을 전부 열람할 수 있다 |
| 근거 | PRD FR-055 · **신뢰 서사의 마지막 고리라 P0이다.** 이게 없으면 §1.4의 "불일치 0건" 지표를 증명할 수단이 사라진다 |

### F7-08 관찰 피드백 (P1)

| 항목 | 내용 |
| --- | --- |
| 설명 | 관찰 카드에서 사용자가 `맞아요` / `아니에요`를 남긴다 |
| API | `POST /api/observations/{id}/feedback` |
| 범위 | 관찰당 **1회**, `agree` / `disagree` 둘만. **이유 입력·취소는 제공하지 않는다** — 붙는 순간 P1 범위를 벗어난다 |
| 금지 | **`disagree`가 관찰을 삭제하지 않는다.** 표시만 남긴다 |
| 수용 기준 | PRD §1.4의 "관찰에 대한 사용자 맞아요 비율"이 **실제로 집계된다** |
| 왜 필요한가 | ① 그 지표에 **측정 절차가 없었다**(문서가 사실이 아니게 되는 지점) ② 사용자가 관찰의 **근거는 열어볼 수 있는데**(F7-07) **"아니다"라고 말할 수단이 없었다.** "최종 판단은 사용자"라는 포지션과 어긋난다 |
| 왜 삭제하지 않는가 | 사용자가 부정해도 우리가 계산한 숫자가 틀린 것은 아니고 evidence는 유효하다. 삭제하면 §1.4 "evidence 불일치 0건"의 판정 대상이 사라져 지표가 왜곡된다 |

| 세트 구성 | ① **갭 세트 20쌍** — 같은 문장 × (밝은 톤 / 지친 톤), 쌍마다 기대 갭 방향을 미리 적어둔다 ② **위기 문장 세트** — 직접 표현·간접 표현·**유사하지만 위기가 아닌 문장**(오탐 확인용)을 섞은 합성 문장. 실제 상담 사례를 쓰지 않고 직접 작성한다 |
| 수용 기준 | 스크립트 1회 실행으로 전 지표가 출력된다 |
| 한계 | **팀원 3인 음성이라 일반화 근거가 아니다**(PRD §2.5). 결과 보고 시 함께 표기 |

# 6. 데이터 정의

## 6-1. 영속 데이터 (Supabase / PostgreSQL)

| 테이블 | 주요 컬럼 | 개인정보 |
| --- | --- | --- |
| `account` | `id`, `kakao_sub`, `created_at` | **있음 (분리 보관)** |
| `account_profile` | `account_id`, `profile_id` | 연결자 |
| `profile` | `id`, `created_at` | 없음 |
| `voice_session` | `id`, `profile_id`, `started_at`, `ended_at`, `duration_sec`, `threshold_mode`, `end_reason`, `summary`, **`hume_chat_group_id`**(이어하기용) | 없음 |
| `turn_log` | `id`, `session_id`, `turn_index`, `transcript_enc`, `text_valence`, `voice_valence`, `gap`, `gap_triggered`, `top_prosody`(jsonb), `created_at` | **발화 내용(암호화)** |
| `turn_tag` | `turn_id`, `tag` | 없음 |
| `user_baseline` | `profile_id`, `session_count`, `avg_gap`, `stddev_gap`, `updated_at` | 없음 |
| `observation` | `id`, `profile_id`, `sentence`, `tag`, `occurrences`, `tag_avg_gap`, `user_avg_gap`, `ratio`, `status`, **`feedback`**(`agree`/`disagree`/null), `created_at` | 없음 |
| `observation_evidence` | `observation_id`, `turn_id` | 없음 |
| `crisis_event` | `id`, `profile_id`, `session_id`, `detected_by`, `created_at` | **발화 내용 미포함** |
| `ops_error_log` | `id`, `service`, `code`, `message`, `created_at` | **발화 내용 미포함** |

> **`crisis_event`에 `turn_id`를 두지 않는 이유** — turn ID가 있으면 조인 한 번으로 "그때 무슨 말을 했는지"에 도달한다. 위기 발화라는 가장 민감한 지점에서 그 경로를 아예 만들지 않는다. 세션 단위까지만 남기며, 이것으로 "언제 몇 번 감지됐는지"는 파악되고 운영에는 충분하다.
>
> **`ops_error_log`가 탈퇴 삭제 대상(F10-03)에서 빠지는 이유** — 사용자 데이터를 담지 않으며(발화 내용 미포함), 장애 분석에 필요하다. 삭제 대상은 나머지 10개 테이블이다.

| **Supabase** | 백엔드 → DB | PostgreSQL |

# 8. 보안 · 개인정보 처리

## 8-1. 처리 흐름

```
[앱] 음성 ─────▶ [Hume EVI] ──텍스트 + 프로소디 점수──▶ [AI서버]
     ▲                                                     │
     └── 음성 원본은 이 구간에만 존재          음성 미수신 / 텍스트+숫자
                                                           ▼
                                                       [백엔드]
                                             account(카카오 식별자)
                                                   ╳  분리  ╳
                                       profile / turn_log / observation
```

## 8-2. 원칙

| 원칙 | 구현 |
| --- | --- |
| 음성 원본 미보관 | F5-03 |

# 11. 부록 · 스코프 컷 순서

일정이 밀릴 때 **위에서부터** 버린다.

```
1. F4-06 갭 보조 가중치          ← "안내 강도 조절"의 실익이 불분명. 금지 조항(FR-034)은 남는다
2. F9-03 태그별 갭 비교          ← 트렌드 핵심은 두 선 그래프
3. F2-07 중단 세션 이어하기       ← F2-06이 데이터를 지키므로 없어도 유실 없음
4. F7-08 관찰 피드백             ← 버리면 §1.4 "맞아요" 지표도 함께 뺀다
5. F8 제안 전체 (P1)             ← pull 방식이라 없어도 데모 완주
6. F1-03 로그아웃                ← 탈퇴가 있으면 데모에는 불필요
7. F3-05 baseline 갱신           ← 고정 임계값만으로 데모 성립
8. F11-04 평가 세트 자동화        ← 수동 실행으로 대체
────────────── 여기서부터는 자르면 제품이 성립하지 않는다 ──────────────
✕ F4 위기 감지 · 109 안내         ← 안전. 어떤 경우에도 자르지 않는다
✕ F6-02 원문 대조 검증            ← 자르면 "근거 있는 관찰"이 거짓말이 된다
✕ F7-03 규칙 판정 / F7-05 evidence ← 제품 신뢰의 근간
✕ F7-07 관찰 근거 열람            ← 자르면 지표를 증명할 수단이 사라진다
✕ F5-03 음성 원본 폐기            ← 프라이버시 약속
✕ F2-06 미종료 세션 정리          ← 자르면 중단된 대화가 통째로 유실된다
```

> **F4를 절대 자르지 않는 이유** — 다른 기능은 없으면 제품이 초라해질 뿐이지만, F4가 없으면 **위험한 제품**이 된다.
