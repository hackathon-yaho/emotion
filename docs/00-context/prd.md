# 1. 제품 개요

## 1.1 한 줄 정의

말로 하루를 이야기하면 AI가 **말투에서** 감정을 읽어 실시간 대화 상대가 되어주고,
쌓인 대화에서 **내가 몰랐던 패턴을 발견해 돌려주며**,
사용자가 원하면 **그 관찰에 근거한 생활 조정을 제안**하는 **모바일 서비스**.

> **웹과 모바일 앱을 모두 지원하고, 배포는 웹으로 한다** — Flutter 단일 코드베이스로 두 타깃을 함께 만든다. 사용 맥락이 늦은 밤·퇴근길의 혼잣말이라(§3.1) 화면은 모바일 폭 기준이다. **배포·제출·시연은 웹 URL**로 하며, 그래서 도그푸딩이 링크 공유로 끝난다 (§14-4).

## 1.2 해결하는 문제

감정을 털어놓을 상대가 필요할 때 사람들은 이미 AI를 찾는다. 그런데 **지금의 AI는 전부 글자만 읽는다.**

| 현재 상태 | 결과 |
| --- | --- |
| ChatGPT·레플리카·에이닷 등은 음성을 **입출력 수단**으로만 사용 | 목소리가 담은 정보가 파이프라인에 아예 들어오지 않음 |
| 텍스트 저널링은 경험을 글로 옮기는 과정에서 비언어 정보가 유실 | 말의 속도, 목소리가 낮아지는 순간이 기록에 남지 않음 |
| 결과적으로 **"저 괜찮아요"라고 말하는데 목소리가 무너진 상태**를 어떤 서비스도 잡지 못함 | 가장 도움이 필요한 순간이 정확히 누락됨 |

**이것은 경쟁사가 게을러서 생긴 공백이 아니라 텍스트 인터페이스의 구조적 한계다.** 입력이 글자면 톤은 애초에 존재하지 않는다.

## 1.3 왜 지금인가

음성 톤에서 감정을 측정하는 API가 **개인 개발자가 무료로 가입해 쓸 수 있는 수준**으로 내려왔고, 그 API가 **한국어를 공식 지원**하며, **대화 응답을 우리 LLM으로 대체할 수 있는 인터페이스(Custom Language Model)**까지 열려 있다. 세 조건이 동시에 성립한 것이 이 제품의 전제다.

```
[2년 전]  음성 감정 인식 = 자체 모델 학습 필요 = 데이터셋 확보부터 프로젝트 하나
[현재]    프로소디 측정 API 구매 + 대화 두뇌는 자체 구현  ← 3인 17일에 가능한 구조
```

## 1.4 성공 지표

> **각 지표를 왜 택했는지를 함께 적는다.** 측정할 수 없거나, 우리가 하지도 않는 주장을 검증하는 지표는 넣지 않는다.

| 구분 | 지표 | 목표 | 측정 방법 | **채택 근거** |
| --- | --- | --- | --- | --- |
| 핵심 | **톤 대비 쌍에서 갭 방향이 기대와 일치** | 90% 이상 | 20쌍 고정 세트 | 우리는 "슬픔 78%" 같은 **절대 감정을 주장하지 않는다**(FR-022). 제품 주장은 "같은 말을 다르게 하면 갭이 갈린다"뿐이므로 검증도 정확히 그것만 하면 충분하다. 절대 감정 정확도를 재는 것은 **하지도 않는 주장을 검증하는 낭비**다 |
| 핵심 | **동일 음성 3회 반복 시 갭 편차** | ±0.1 이내 | 재현성 측정 | 갭이 같은 입력에 흔들리면 대시보드의 추세선 전체가 무의미해진다. 정확도보다 **재현성이 먼저** 성립해야 하는 지표다 |
| 안전 | **위기 발화 재현율** | 95% 이상 | 합성 문장 세트 | 놓쳤을 때의 비용이 비대칭적으로 크다. 이 기능만 정밀도가 아닌 **재현율 우선**으로 운영한다(FR-032) |
| 안전 | **관찰 문장 ↔ evidence 숫자 불일치** | **0건** | 배치 결과 전수 검사 | 이 제품에서 가장 위험한 실패는 **없는 패턴을 지어내는 것**이다. 감정 앱에서 이것은 단순 버그가 아니라 사용자가 자기 인식을 왜곡하게 만드는 해다. 코드로 증명 가능한 유일한 방어선 |
| 안전 | **발화 원문에 없는 태그 발생** | **0건** | 코드 대조 | 위와 같은 이유. 태깅은 LLM이 하되 **원문에 등장한 표현만** 허용하므로, 이 값이 0이 아니면 검증 로직 자체가 깨진 것이다 |
| 안전 | **텍스트 valence·응답 LLM 입력에 프로소디 포함** | **0건** | 코드 대조 (payload 검사, TC-24) | 갭의 전제는 "텍스트는 텍스트만, 음성은 음성만"이다. 텍스트 쪽 LLM이 프로소디를 보면 텍스트 valence가 음성에 끌려가 **갭이 스스로 줄어든다** — 두 선 그래프와 되묻기가 구조적으로 약해진다(FR-025) |
| 품질 | 응답 지연 (발화 종료 → 첫 음성 출력) | p95 2초 이내 | 세션 계측 | 실시간 대화 제품에서 사용자가 체감하는 품질은 사실상 이 하나다. 우리 아키텍처는 이 값을 지키려고 홉을 줄인 구조다(§6) |
| 품질 | 데모 플로우 무중단 완주 | 100% | 리허설 | 실시간 음성이라 데모 실패 리스크가 구조적으로 높다(§13) |
| 보조 | 관찰에 대한 사용자 "맞아요" 비율 | 목표치 없음 | **F7-08 피드백 버튼으로 수집**(FR-056) | 표본이 팀원 3인이라 **통계적 주장을 할 수 없고**, 목표를 걸면 숫자를 맞추려는 압력이 생긴다. 참고값으로만 본다 |

> **평가 세트는 팀원 3인이 직접 녹음한 20쌍이다.** 외부 데이터셋을 쓰지 않는 이유는 공개 음성 감정 데이터셋이 대부분 **영어권 연기 감정**이라(§2.2) 한국어 실사용 톤과 어긋나기 때문이다. 3인 음성이라는 한계는 §2.5에 명시한다.

# 3. 대상 사용자

## 3.1 세그먼트 정의

**타겟을 인구통계로 좁히지 않는다**(decisions.md #4). 이 제품은 처방 도구가 아니라 **대화 상대**이고, "감정을 말할 상대가 필요한 순간"은 직업·연령으로 구획되지 않는다. 대신 **사용 맥락**으로 정의한다.

| 맥락 | 설명 |
| --- | --- |
| 말할 상대가 없는 시간대 | 늦은 밤, 퇴근길, 혼자 있는 주말 |
| 말하기엔 사소한 일 | 남에게 꺼내기엔 작지만 마음에 남은 감정 |
| 텍스트로 쓰기엔 지친 상태 | 저널링을 시도했다가 사흘 만에 그만둔 경험 |

## 3.2 페르소나

### P-01 · 재택근무 직장인 (34세)
하루 종일 말할 일이 없다. 저녁이면 이유 없이 가라앉는데 원인을 모른다. 일기 앱을 세 번 깔았다 지웠다.
→ **관련 기능**: F2 음성 대화, F7 패턴 발견, F9 대시보드

### P-02 · 감정을 축소해서 말하는 사용자 (29세)
힘들어도 "괜찮다"고 말하는 습관이 있다. 본인도 자기 상태를 잘 모른다.
→ **관련 기능**: F3 갭 측정, F4 되묻기 · **제품의 핵심 가치가 가장 선명하게 작동하는 페르소나**

### P-03 · 기록을 남기고 싶은 사용자 (41세)
꾸준히 기록하고 싶지만 글쓰기가 부담이다. 지난 감정을 돌아보는 데 관심이 있다.
→ **관련 기능**: F5 대화 기록, F9 대시보드

### P-04 · 프라이버시 민감 사용자 (37세)
감정 데이터를 남기는 것 자체가 불안하다. "이거 어디 저장되나요"를 먼저 묻는다.
→ **관련 기능**: F10 데이터 관리, 음성 원본 미저장 정책

### P-05 · 위기 근접 사용자
평소처럼 말하지만 목소리에 신호가 있다. 직접적인 표현은 쓰지 않는다.
→ **관련 기능**: F4 위기 감지, 109 안내 · **이 페르소나 때문에 F4가 P0이다**

## 4.3 감정 측정 (FR-020~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-020 | 발화마다 프로소디 점수에서 **음성 valence**를 산출한다. 48종 감정 → ±1 매핑표는 **코드 상수**이며 결정적으로 동작한다 | P0 |
| FR-021 | **텍스트 valence**는 프로소디를 입력에서 배제한 **별도 경량 LLM 호출**(전사 텍스트 + 텍스트 이력만 입력)로 산출한다. 응답 호출 **앞에** 위치하며 타임아웃 400ms, 동일 전사는 캐시로 결정적이다 | P0 |
| FR-022 | **갭 = \|텍스트 valence − 음성 valence\|** 로 정의한다. 절대 감정 상태를 단정하지 않는다 | P0 |
| FR-023 | 임계값은 **세션 5회 미만이면 고정값, 5회 이상이면 개인 평균 ± 표준편차**를 사용한다 | P0 (전환 P1) |
| FR-024 | 텍스트 valence 호출 실패·타임아웃 시 갭을 산출하지 않고, 되묻기 없이 평범하게 응답한다(폴백) | P0 |
| FR-025 | 응답 LLM과 텍스트 valence LLM의 입력에 **프로소디 48종 원본을 포함하지 않는다.** 응답 LLM에는 계산된 **플래그**(갭 트리거·위기·마무리·조언 요청)만 전달하고, valence·갭 **수치**도 전달하지 않는다 | P0 |

> **FR-022가 정확도 반박을 차단한다** — 절대 감정을 단정하지 않고 두 채널의 **차이**만 보므로 개인별 음성 편차에 강하고, 틀려도 "아닌데요?"로 끝나는 대화의 단서일 뿐이다.
> **FR-023 근거** — 원래 목소리가 낮고 차분한 사용자는 고정 임계값에서 매번 오탐을 맞는다. 반대로 개인 baseline만 쓰면 **첫 사용자에게 baseline이 없어 데모 첫 장면이 작동하지 않는다.** 두 실패를 모두 피하는 유일한 구성이 하이브리드다. 전환 기준 5회는 도그푸딩 기간(9/10~9/20) 안에 **전환이 실제로 일어난 로그를 확보**할 수 있는 값이다.
> **FR-021·025 근거** (2026-09-03 개정) — 원안은 텍스트 valence를 응답 호출의 첫 줄로 받았으나, 되묻기가 갭 판정 **결과**를 같은 호출의 입력으로 써야 하는 **순환 의존**이 있었고(같은 호출의 출력을 입력으로 쓸 수 없다), 응답 LLM이 프로소디를 보면 텍스트 valence가 음성에 끌려가 **갭이 스스로 줄어드는** 문제가 있었다. 분리 호출의 지연(+300~400ms)은 NFR-01 안에서 감당하고, 초과 시 추측 실행으로 전환한다. 태그·위기 LLM 판정도 분석 호출로 옮겨 **응답 스트림에 메타 태그가 없다.** 상세는 [ai-pipeline.md](../02-architecture/ai-pipeline.md) §2. 개정 요청: `request/ai/clm-turn-pipeline-review.md`.

## 4.4 대화 트리거 및 안전 (FR-030~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-030 | 갭이 임계를 넘으면 AI가 **먼저 되묻는다**. 갭 수치 자체는 대화 화면에 노출하지 않는다 | P0 |
| FR-031 | 갭 수치는 **기록·트렌드 화면에서만** 시각화한다. 데모 모드에서는 대화 화면에도 노출한다 | P0 |
| FR-032 | 위기 발화는 **키워드 규칙 OR LLM 판정**으로 감지한다. 둘 중 하나만 걸려도 감지로 처리한다 | P0 |
| FR-033 | 위기 감지 시 대화 톤을 전환하고 **109 안내**를 제시한다. 서비스를 중단하거나 대화를 차단하지 않는다 | P0 |
| FR-034 | 갭 지수를 **위기 감지의 단독 트리거로 쓰지 않는다** | P0 |
| FR-035 | 진단명·약물·치료를 언급하지 않는다. 프롬프트 가드로 차단한다 | P0 |
| FR-036 | 이미 위기가 감지된 상태에서 갭이 극단적이면 **안내 강도를 조절**한다 | P1 |

> **FR-034와 FR-036을 분리한 이유** — 하나에 묶으면 우선순위가 성립하지 않는다. **금지(FR-034)는 안 지키면 평범한 피로에 상담 안내가 떠서 사용자를 쫓아내므로 P0**이고, **가중치(FR-036)는 없어도 안내가 나가므로 P1**이다. FR-036을 스코프에서 잘라내도 FR-034는 그대로 적용된다.

> **FR-030 근거** — 털어놓는 중에 "불일치 1.32"가 뜨면 관찰당하는 느낌이 된다. 위로받으러 온 사용자에게 정반대의 경험이며, "확정 진단이 아니라 대화의 단서"라는 포지션도 무너진다.
>
> **오탐 정책이 기능군마다 반대인 이유**
>
> | 기능 | 정책 |
> | --- | --- |
> | 갭·패턴 발견 | **정밀도 우선** — 애매하면 침묵 |
> | 위기 감지 | **재현율 우선** — 애매하면 감지 |
>
> 패턴을 잘못 말하면 신뢰를 잃지만 위기를 놓치면 사람이 다친다. 오탐의 비용은 안내 한 줄이 한 번 더 뜨는 것뿐이다.
>
> **FR-034 근거** — 피곤한 날의 말투와 위기 발화는 프로소디만으로 구분되지 않는다. 갭을 단독 트리거로 쓰면 평범한 피로에 자살예방 상담 안내가 떠서 사용자를 쫓아낸다.
>
> **FR-032에서 규칙을 남기는 이유** — LLM 판정만 두면 FR-024의 폴백 경로(LLM 형식 오류)에서 **위기 감지가 함께 죽는다.** 안전 기능이 다른 기능의 실패에 연동되어서는 안 되므로, 항상 도는 키워드 매칭을 최후 방어선으로 둔다.

## 4.5 로그 및 주제 태깅 (FR-040~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-040 | 턴마다 텍스트·valence 2종·갭·태그·프로소디 상위 점수를 백엔드에 적재한다 | P0 |
| FR-041 | **음성 원본은 저장하지 않는다.** 분석 직후 폐기하며 서버·스토리지 어디에도 남기지 않는다 | P0 |
| FR-042 | 발화 텍스트는 암호화하여 저장한다. 관찰의 evidence 열람에 사용된다 | P0 |
| FR-043 | 주제 태그는 LLM이 추출하되 **발화 원문에 실제로 등장한 표현만** 허용한다. 원문에 없는 태그는 코드가 검사해 폐기한다 | P0 |

> **FR-043 근거** — 순수 규칙 기반 키워드 추출은 한국어에서 세 가지가 무너진다. ① 활용형이 쪼개진다(`회의가`·`회의를`·`회의`가 각각 집계되어 실제 16회인 주제가 3회 미만으로 사라진다) ② `오늘`·`진짜`·`사람` 같은 무의미어가 상위를 차지한다 ③ `회의`·`미팅`·`팀장님`이 하나로 묶이지 않는다. 형태소 분석기와 불용어 사전을 붙이는 것보다 LLM 호출 한 번이 짧다. **단 ③의 동의어 병합은 v1에서 하지 않는다** — `미팅`이라고 말한 턴에 `회의`를 달면 원문 대조(아래)에 걸리기 때문이다. 활용형 정규화(`회의가`→`회의`)와 세션 내 기본형 통일까지만 한다 (2026-09-03, [ai-pipeline.md](../02-architecture/ai-pipeline.md) §6.2).
> 다만 **환각이 위험한 것은 판정이지 태깅이 아니다.** 태깅은 눈앞의 발화 하나만 보고 라벨을 붙이는 구조화 작업이므로, 원문 대조 검사로 규칙 기반과 동일한 안전성을 확보한다.

## 4.6 패턴 발견 (FR-050~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-050 | 세션 종료 후 **비동기 배치**로 태그별 갭·valence를 집계한다 | P0 |
| FR-051 | 관찰은 **같은 태그 3회 이상 AND 해당 태그 평균 갭이 개인 전체 평균의 1.5배 이상**일 때만 생성한다 | P0 |
| FR-052 | 조건 미달이면 **아무 관찰도 만들지 않는다.** 매일 억지로 통찰을 생성하지 않는다 | P0 |
| FR-053 | 관찰에는 반드시 **evidence**(태그, 등장 횟수, 태그 평균 갭, 개인 평균 갭, 비율, 근거 turn ID 목록)를 첨부한다 | P0 |
| FR-054 | LLM은 **표현만** 담당한다. 패턴의 존재 여부·강도를 LLM이 판정하지 않는다 | P0 |
| FR-055 | 사용자는 관찰 화면에서 evidence의 **실제 대화로 내려갈 수 있다** | P0 |
| FR-056 | 사용자는 관찰에 `맞아요` / `아니에요`를 남길 수 있다. **`아니에요`가 관찰을 삭제하지는 않는다** | P1 |

> **FR-056 근거** — ① §1.4의 "관찰에 대한 사용자 맞아요 비율" 지표에 **측정 절차가 없었다.** 수집 수단 없는 지표는 문서를 사실이 아니게 만든다. ② 사용자가 관찰의 **근거는 열어볼 수 있는데**(FR-055) **"아니다"라고 말할 수단이 없었다.** "최종 판단은 사용자"라는 포지션과 어긋난다.
> **삭제하지 않는 이유** — 사용자가 부정해도 우리가 계산한 숫자가 틀린 것은 아니고 evidence는 유효하다. 삭제하면 §1.4 "evidence 불일치 0건"의 판정 대상이 사라져 지표가 왜곡된다.

> **판정 권한을 LLM에 주지 않는 이유** — 로그를 통째로 주면 LLM은 그럴듯한 패턴을 반드시 만들어낸다. 사용자가 "내가 정말 그랬나" 하고 믿게 되는 종류의 거짓이라, 감정 앱에서는 버그가 아니라 **자기 인식을 왜곡시키는 해**다. 판정을 규칙으로 고정하면 모든 관찰이 숫자로 역추적되고 §1.4의 "불일치 0건" 지표로 증명 가능해진다.
> **FR-052 근거** — 매일 통찰을 뱉는 앱은 금세 신뢰를 잃는다. 침묵할 수 있어야 말할 때 믿긴다.

## 4.7 제안 (FR-060~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-060 | 제안은 **사용자가 요청할 때만** 제시한다(pull). AI가 먼저 조언을 밀어넣지 않는다 | P1 |
| FR-061 | 모든 제안은 **특정 관찰을 근거로** 달고 나온다. 근거 없는 일반론 조언을 금지한다 | P1 |
| FR-062 | 제안 범위는 **일정·습관·환경 조정**까지로 한정한다. 진단·약물·치료는 금지 | P1 |

> **pull 방식인 이유** — "전문가도 아닌데 조언해도 되나요?"라는 심사 질문에 "사용자가 물어서 답했습니다"로 정리된다. 밀어붙이는(push) 방식은 이 방어가 불가능하다.
> **FR-061 근거** — "규칙적인 수면이 중요해요"는 ChatGPT도 하는 말이라, 근거 없는 조언을 허용하는 순간 우리 차별점을 스스로 지운다.

## 4.8 대시보드 (FR-070~)

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| FR-070 | 기간별 **텍스트 valence와 음성 valence를 두 개의 선**으로 함께 표시한다 | P0 |
| FR-071 | 두 선이 벌어진 구간을 시각적으로 강조한다 | P0 |

## 4.9 데이터 관리 (FR-080~)

| ID | 요구사항 | 우선 |

| FR-080 | 보관 기간 자동 만료를 두지 않는다. 사용자가 삭제할 때까지 유지한다 | P0 |
| FR-081 | 세션 단위 삭제를 제공하며, **그 세션을 근거로 삼던 관찰도 함께 무효화**한다 | P0 |
| FR-082 | 온보딩과 설정에서 "음성 원본은 저장하지 않는다"를 명시한다 | P0 |

> **자동 만료를 두지 않는 이유** — 확장성 논거가 "쓸수록 나를 알아간다"인데(decisions.md #13) 90일 롤링 삭제는 그 축적을 스스로 지운다. "작년 이맘때도 같은 패턴이었다"가 이 제품이 도달할 수 있는 가장 좋은 순간인데 만료가 있으면 영원히 도달하지 못한다. 기간 제한 대신 **삭제 권한**으로 신뢰를 확보한다.
> **FR-081 근거** — 근거 대화가 삭제됐는데 관찰만 남으면 그 관찰은 그 순간 "근거 없는 문장"이 된다. §1.4의 불일치 0건 지표와 직접 연결된 요구사항이다.

       │                        │   AI 서버     │
       │                        │  CLM 수신     │  ◀── SSE 응답 ────────
       │                        │  갭 계산      │

# 7. 데이터 모델 (Supabase / PostgreSQL)

| 테이블 | 용도 | 개인정보 |
| --- | --- | --- |
| `account` | 카카오 식별자, 가입 시각 | **있음 (분리 보관)** |
| `account_profile` | `account` ↔ `profile` 매핑 | 연결자 |
| `profile` | 내부 사용자 ID. 감정 데이터의 유일한 참조 대상 | 없음 |
| `voice_session` | 대화 세션. 시작·종료 시각, 길이, 임계 모드, 종료 사유, **Hume chat group ID**(이어하기용) | 없음 |
| `turn_log` | 턴별 발화 텍스트(암호화), valence 2종, 갭, 트리거 여부, 프로소디 상위 점수 | **발화 내용** |
| `turn_tag` | 턴 ↔ 태그 | 없음 |
| `user_baseline` | 세션 수, 평균 갭, 표준편차 | 없음 |
| `observation` | 관찰 문장, 태그, 등장 횟수, 태그 평균 갭, 개인 평균 갭, 비율, 상태, **사용자 피드백** | 없음 |
| `observation_evidence` | 관찰 ↔ 근거 turn | 없음 |
| `crisis_event` | 위기 감지 시각, 감지 경로(rule/llm), **세션 단위까지만** | 발화 내용 미포함 |
| `ops_error_log` | 오류 로그 | 발화 내용 미포함 |

> **`crisis_event`에 turn ID를 두지 않는다.** turn ID가 있으면 조인 한 번으로 "그때 무슨 말을 했는지"에 도달한다. 가장 민감한 지점에서 그 경로를 아예 만들지 않는다.
> **`ops_error_log`는 탈퇴 삭제 대상이 아니다.** 사용자 데이터를 담지 않으며 장애 분석에 필요하다. FR-003의 삭제 대상은 나머지 10개 테이블이다.

# 9. AI 파이프라인 명세

## 9.1 실시간 턴 처리

> **2026-09-03 개정.** 상세 설계의 단일 출처는 [ai-pipeline.md](../02-architecture/ai-pipeline.md) §2다. 여기는 요지만 둔다.

```
① Hume → AI서버     messages[] 전체 이력 수신. 마지막 user 턴의 전사 T, 프로소디 P
② 세션 컨텍스트     임계 모드·임계값·시작 시각 (백엔드 조회, 세션당 1회 캐시)
③ 병렬 ┬ voice_valence  P → 매핑표 → (P−N)/(P+N)                    ← 규칙, 결정적
       ├ 위기 규칙       T 키워드 매칭(Tier A)                          ← 규칙, 항상 동작
       └ 분석 호출       T + 텍스트 이력만 → text_valence·태그·위기(LLM)  ← 프로소디 미노출, 타임아웃 400ms
④ 규칙 판정         gap = |text − voice| vs 임계값 · crisis = 규칙 OR LLM · 태그 원문 대조
⑤ 응답 호출         텍스트 이력 + 플래그(gapTriggered·crisis·softWrap·adviceRequested)만 → 대화 텍스트
⑥ SSE 반환          본문 그대로 스트리밍. 메타 태그 없음, 버퍼링 없음
⑦ 로그 적재         POST /internal/turns (비동기. user 턴은 ④ 직후, assistant 턴은 스트림 종료 후)
```

**호출을 둘로 나눈 이유** — 되묻기는 갭 판정 **결과**를 입력으로 받아야 하는데, 텍스트 valence가 응답 호출의 출력이면 같은 호출 안에서 순환한다. 또 응답 LLM이 프로소디를 보면 텍스트 valence가 음성에 끌려가 갭이 줄어든다. 분석 호출을 앞에 두고 프로소디를 완전히 가리면 둘 다 해소된다. 텍스트 valence·태그·위기 판정이 전부 분석 호출로 가므로 **응답 스트림에는 메타 태그가 없다** — 파싱·제거 코드가 존재하지 않는다.

# 12. 일정

에이전트 기반 개발이므로 개발 타임라인은 세우지 않는다. **외부에서 정해진 고정 마감은 제출 하나뿐이고, 나머지는 팀 내부 목표다.**

| 날짜 | 항목 | 성격 | 최소 조건 |
| --- | --- | --- | --- |
| 2026-09-10 | 팀 3인 매일 3분 실사용 시작 | **목표** (2026-09-04 조정) | 녹음 + STT + 프로소디 점수 저장만 되면 된다. 갭 계산·대시보드는 이후에 붙어도 데이터는 쌓인다 |
| **2026-09-20** | **제출** | **고정** | — |

**도그푸딩 시작 시점은 배포 시점에 종속된다.** 앱이 웹이고 3인이 각자 기기에서 접속하므로(§14-4), 백엔드·AI서버가 로컬에만 있으면 실사용이 성립하지 않는다. **배포는 세 파트의 기능 확인이 끝난 뒤에 한다**(2026-09-04 팀 결정).

**개발은 하루로 압축할 수 있어도 "10일치 감정 로그"는 10일이 걸린다.** 발표의 "발견" 장면은 이 데이터에만 의존한다. 그래서 9/10을 목표로 두되, **밀릴 경우의 대가를 알고 밀어야 한다** — 로그 기간이 짧아지면 관찰 생성 조건(같은 태그 3회 이상 AND 개인 평균 갭의 1.5배 이상, FR-051)에 미달해 **S03 발견 화면이 빈 상태로 심사받을 수 있다.** 조건 미달 시 억지 관찰을 만들지 않는 것이 이 제품의 설계이므로(FR-052), 데이터가 부족하면 화면은 정직하게 비어 있다.

> **데이터 원칙: 샘플 데이터는 개발·테스트 전용, 발표 근거는 실사용 로그만.** 시뮬레이션 그래프는 "직접 만드신 거죠?" 한 마디에 발견 기능 전체를 연출로 격하시킨다.

## 14-4. 앱 프레임워크 결정 (2026-09-03, 프론트)

**Flutter로 확정한다. 웹과 모바일 앱을 모두 지원 타깃으로 두고, 배포는 웹으로 한다.** 둘 사이에 우선순위를 두지 않는다 — 하나의 코드베이스에서 함께 나오므로 나눌 이유가 없다.

| 결정을 규정한 제약 | 내용 |
| --- | --- |
| 제품 형태가 모바일이다 | 사용 맥락이 늦은 밤·퇴근길의 혼잣말이라(§3.1) 손에 쥔 기기가 기본이다. 화면은 웹·앱 모두 모바일 폭 기준으로 만든다 |
| **배포는 웹으로 한다** | 제출물의 서비스 링크가 웹 URL이고, **웹이면 도그푸딩 배포가 링크 공유로 끝난다** — 스토어 심사·인증서·기기 등록·APK 배포가 전부 없어져 **9/10 시작일 리스크가 사라진다**(§12). 고치면 즉시 3인 전원에 반영된다 |

| 브라우저 실행 | 정상 렌더 |
| EVI 세션 수립 | **성공.** `chat_metadata` 수신 — `chat_group_id`·`chat_id` 실물 확인 (F2-07 이어하기의 `resumedChatGroupId` 원천) |
| 초기 로드 실측 | `main.dart.js` 2.0MB + CanvasKit 5.2MB ≈ **7MB.** 축소는 앱 담당 과제 |
| **마이크 → 음성 왕복** | **미검증.** 위 경로까지 성립하므로 동작을 전제로 착수한다. 실패하면 전환 대상은 React + Hume 공식 React 클라이언트 SDK |

**"둘 다 지원"과 "웹 배포"가 충돌하지 않는 이유** — 지원 타깃은 **어디서 도는가**의 문제이고, 배포는 **어떻게 전달하는가**의 문제다. 웹·iOS·Android 빌드가 같은 코드에서 나오므로 셋 다 유지하되, 도그푸딩·심사 시연·제출은 전부 같은 URL 하나로 끝낸다. 앱 빌드는 언제든 뽑을 수 있는 상태로 둔다.

**남은 리스크** — Hume은 Python·TypeScript·React 클라이언트 SDK만 공식 제공하고 **Dart/Flutter SDK는 없다.** 공식 예제 1개에 의존하므로, EVI 프로토콜 변경이나 오디오 버그를 만나면 React 경로보다 지원이 얇다. 이 리스크를 알고 택한 것이며, 전환 판단은 위 표의 마지막 행에 걸린다.
